# Implementation Plan: Testimonial Carousel (Phase 4)

**Branch**: `004-testimonial-carousel` | **Date**: 2026-04-02 | **Spec**: [spec.md](./spec.md)
**Input**: LAUNCH_MATRIX.md Section 14, Phase 4 (tasks 4.1–4.9)

## Summary

New feature: testimonial carousel where users upload messaging screenshots that are rendered as platform-accurate mockup slides. Hook slide (AI-generated), middle slides (one testimonial per slide in platform frame), close slide (CTA). Supports cold (curiosity hook) and retargeting (objection-connected hook). Platform detection runs server-side during generation, not during upload.

## Technical Context

**Language/Version**: TypeScript 5.7 (functions), TypeScript 5.9 (frontend)
**Primary Dependencies**: Firebase Cloud Functions v2, Gemini 3.1 (text + image), React 19
**Storage**: Testimonial screenshots stored as base64 in request payload (same as personalPhotos). No separate storage.
**Testing**: Contract fixtures (`npm run test:contracts`)
**Target Platform**: Web — Firebase Hosting + Cloud Functions
**Project Type**: SaaS web application
**Performance Goals**: Platform detection + N mockup renders must complete within the existing 300s Cloud Function timeout. Mockup renders can run in parallel.
**Constraints**: Platform detection is server-side batch (during generation). Upload shows generic badge. Mockup frames generated by Gemini VISUAL_MODEL, not static compositing.

## Key Design Decisions

### Platform Detection Approach

**Decision**: Use Gemini VISUAL_MODEL (gemini-3.1-flash-image-preview) with a structured prompt asking it to identify the platform from the screenshot.

**Rationale**: The project already uses Gemini for image analysis. A single vision call with a structured JSON response is simpler and more accurate than building a heuristic-based detector. Flash model keeps cost low.

**Alternative rejected**: Client-side heuristics (color matching, UI element detection) — too fragile across platform UI updates and dark/light modes.

### Mockup Frame Generation

**Decision**: Use Gemini VISUAL_MODEL to generate the mockup frame by prompting it to render the testimonial screenshot inside the platform UI. The screenshot is passed as an image input alongside the platform-specific prompt.

**Rationale**: Consistent with existing image generation pipeline. Avoids adding Sharp/Canvas dependencies for server-side compositing. The AI model naturally handles different screenshot sizes and platform variations.

**Alternative rejected**: Static template compositing with Sharp — would require maintaining 7 pixel-perfect platform templates that break when platforms update their UI.

### Slide Generation Pipeline

The testimonial carousel pipeline integrates into the existing generation flow:

1. User uploads screenshots + selects testimonial_carousel mode
2. Generation starts → `generateTestimonialCarousel()` is the entry point
3. Platform detection: batch call to Gemini VISUAL_MODEL for all screenshots
4. Hook slide: Gemini CREATIVE_MODEL generates hook text (cold: curiosity, retargeting: objection+tease)
5. Middle slides: Parallel Gemini VISUAL_MODEL calls, one per testimonial (screenshot + platform mockup prompt)
6. Close slide: Gemini CREATIVE_MODEL generates close text + CTA
7. All slides assembled into CarouselResult
