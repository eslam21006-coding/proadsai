# Feature Specification: Cumulative Learning for Ad Performance

**Feature Branch**: `969-cumulative-learning`
**Created**: 2026-09-02
**Status**: Draft
**Input**: User description: "Build cumulative learning for the ad performance system. The learning aggregates do not accumulate — each sync rebuilds an angle's aggregate entirely from that sync's ads and overwrites the stored record. Changing funnel settings rewrites verdicts and shrinks the counts; a partial sync silently shrinks the signal. Persist the evaluation context, freeze the per-ad verdict at write time, make aggregates truly cumulative and idempotent, record funnel type for weighting (never exclusion), and update the retrieval and dashboard readers. No epoch partitioning. No backfill or migration."

**Source of truth for current state**: `docs/investigations/learning-cumulative-investigation.md` (every finding verified against code with file:line evidence).

---

## Context: What Is Broken

The account owner stated the requirement verbatim:

> "I don't want to be working on a low-ticket funnel and having an amazing learning experience, only to have everything reset once I switch to another funnel. It should be accumulative. When something works in a specific funnel, we should use that learning in different funnels."

Three defects produce the reset the owner experiences:

1. **The aggregate is rebuilt, not accumulated.** Each sync computes an angle's record entirely from that sync's ads and replaces the stored record. Nothing merges with history (investigation §3.2).
2. **The evaluation context is discarded.** The cost target an ad was judged against is loaded once per sync, used to produce a win/lose mark, and then dropped. Nothing records what the ad was measured against, so no past result can be compared to a present one (investigation §2.2).
3. **The same ad is counted again on every sync it appears in.** There is no record of what an ad has already contributed, so contribution is neither idempotent nor retractable (investigation §3.5).

The consequence is that an ad judged a winner under a $50 target becomes a non-winner under a $30 target on the very next sync, and the angle's winner count falls — even though nothing about the ad's actual performance changed. A sync that covers only part of the account has the same effect on the angles it happened to touch.

## Context: Decisions Already Locked

These are settled and are not re-opened by this specification:

- **No epoch partitioning.** Partitioning learning by epoch and resetting on funnel-type change is rejected. It destroys the accumulated value the owner is asking to preserve.
- **No backfill, no migration.** There are no active users. Existing aggregate records carry frozen counts whose original target is unrecoverable. They are **retired**, not converted. Learning starts clean.
- **Click-through and cost-per-thousand behaviour is preserved.** Those measures are target-independent and already span funnel types. Their meaning, units, and funnel-blindness do not change.
- **The verdict engine is not in scope.** It computes correctly. The defect is at the write site, not the compute site.

## Clarifications

### Session 2026-09-02

- Q: An ad evaluated before funnel economics are resolvable seals with no target, and FR-011's two material-change triggers do not include settings completion — so it can never gain an efficiency figure. How should this be handled? → A: Option A — provisional until sealable. The contribution is marked PROVISIONAL and contributes usage and click-through immediately; the first evaluation at which a target is resolvable seals it. The transition is one-way and MUST be enforced in code, not by convention: no path — settings change, re-sync, manual refresh, or economics version bump — may return a SEALED ad to PROVISIONAL. Sealing uses the target resolvable **at the moment of sealing**, not backdated to when the ad ran; this is a known and accepted imprecision. While PROVISIONAL, the ad's click-through contribution **does** count toward the guidance activation threshold, because that threshold gates click-through-driven guidance and click-through is target-independent; the efficiency figure retains its own separate evidence gate.
- Q: How do concurrent and duplicate syncs resolve, given the ledger's read-compare-write is not atomic and Cloud Tasks retries can redeliver an identical payload? → A: Option A — serialize per account with a lease, subject to five conditions. The lease MUST expire on its own after **15 minutes** (derived from the platform's 540-second execution ceiling, not estimated). It MUST cover **only the learning write**, not the whole sync, since concurrent Meta fetches are harmless and only the check-then-act is racy. Acquisition and release MUST be atomic via a **transaction over a single lease document**, and release MUST verify holder identity. The **manual** path fails fast with a bilingual message; the **scheduled** path MUST NOT fail silently and instead signals failure so the existing task retry configuration re-dispatches it. A run MUST re-verify it still holds the lease immediately before committing and abort if it does not; the residual window between check and commit is acknowledged explicitly rather than papered over.
- Q: The contribution ledger lives on the ad document and is now load-bearing for correctness, but the sync reads that collection with an unbounded scan that grows with account age. How is ledger durability reconciled with that read? → A: Option A — permanent ledger, bounded read. Ad documents MUST never be pruned, with the reason recorded at the write site so a future retention policy hits it before the code is written. The unbounded scan MUST be **removed entirely**, not left alongside the new read, and replaced by a by-ID read over exactly the current batch — chunked at **300** (a value-list query caps at 30, too small; a multi-document fetch has no documented count cap, so the chunk is policy), with every chunk completing before any write. A failed chunk read MUST abort the learning write for that chunk rather than read as "no prior contribution", since conflating the two produces the double-count FR-018 forbids; this needs its own test. Reads MUST return whole documents, not projections, or cascade-written fields are lost. Three non-learning behaviours share this read — the match-link precedence lock, the delete-cascade preservation flag, and the match tallies — and are explicitly in scope; all three are per-ad lookups for ads already in the batch, so the bounded read is behaviour-identical for each.
- Q: FR-051 required an audit record "sufficient to explain why any count is what it is", which read literally means per-ad logging — contradicting the sync path's standing convention of one line per account, written specifically to prevent log spam. How is auditability structured? → A: Option A — layered. The **ledger is the per-ad audit trail**; logs must not duplicate what it already stores durably. Logs emit one summary line per account per sync, with skips **broken down by enumerated reason** rather than a single bucket. Individual event lines are permitted only for events that cannot fire in bulk. Two events initially classified as rare are not: **seal transitions** are bimodal (zero in steady state, then the entire provisional backlog at once when settings complete), and **refresh withdrawals are the modal case** — a live ad's rolling metrics move nearly every sync, making withdraw-then-add the common path for every active ad rather than an exception. Both are counts. Only re-attribution withdrawals, lease acquisition failures, lease-lost-mid-write, and ledger chunk read failures get individual lines. Log content is restricted to identifiers, state names, reason codes, and counts — no owner-facing strings, no governed metric names, no percentages — following the funnel-settings observability precedent. The automated guard for governed metric names does not walk the backend tree, so this is **stated but not enforced**, and that gap is recorded deliberately.

### Session 2026-09-05

- Q: FR-084 keys accrual on (ad row id, date) and FR-066 forbids pruning ad documents. Where are per-day conversion figures stored, and for how long? → A: **Bounded retention, and it is mandated rather than preferred.** Retain per-day entries only for days still inside the observed window; on finalisation (FR-083) discard the individual entry and fold it into a running finalised total plus a count of finalised days (FR-084a). Unbounded retention would breach **SC-023** through **FR-071** — whole-document by-ID reads would grow with account age — so this is required by requirements already in the spec, not a storage optimisation. Nothing is lost: a finalised day is immutable and window membership is pure date arithmetic. The count is retained alongside the total so the total can be sanity-checked, and because FR-086 needs it as an input. Accepted cost recorded against FR-051a: the ledger can no longer answer "which days composed this total", which is consistent because FR-051a's guarantee is over contributions to aggregates, not over day-level accrual.
- Q: FR-079 says the efficiency figure is written once and never revised; FR-080 says withdraw-then-add survives for attribution changes. On re-attribution, is the figure recomputed or carried across? → A: **Carried across unchanged.** Governed by the single recomputation rule **FR-087**: the figure is recomputed when the creative's **set of rows** changes, and carried across when only its **destination** changes. A re-attribution keeps every row and the sealed target, so the inputs are unchanged and the output must be. FR-080 moves **where** the figure is counted; FR-079 governs **what the number is** — once that distinction is stated they are orthogonal, and SC-035 and SC-036 both hold independently.
- Q: When FR-074b merges two hash groups that have each already sealed, which sealed target survives, and what happens to figures both have already contributed? → A: **Recompute over the union; the earliest sealed target survives.** A merge changes the row set, so FR-087 requires recomputation — the two pre-merge figures were each computed over half the evidence, because the split was a mis-identification rather than a real division. No new target rule is needed: **FR-012a is rephrased** from "the first row of that creative to seal" to "the earliest-sealing row among all rows now belonging to the creative", so a merge simply widens the set the existing rule ranges over. Where both halves had contributed, **FR-013a** requires withdraw-both, recompute over the union, add one, with both withdrawals completing before the addition. A merge is an **identity correction** and belongs under FR-080's exception, not under FR-079's prohibition.
- Q: Meta returns no daily row for a day on which an ad did not deliver. Is that zero conversions or no observation — and does it feed the days-lost-to-gaps count? → A: **Not observed, never zero (FR-085a)** — writing zero is drawing evidence from absence, which the edge-case list already forbids for an ad and which applies identically to a day. **And the count must track a different thing (FR-086a):** days-lost tracks dates **no sync's window covered**, not dates for which Meta returned no row. A date inside an observed window with no row means the ad did not run and is **not** a gap; a date outside every observed window is unrecoverable and **is** one. Conflating them would make the count non-zero continuously for any paused ad, so a real outage would arrive as noise inside noise.
- Q: With FR-054a placing the lease inside `runSyncForAccount`, does a failed acquisition fail the whole account sync, discarding operational writes that already succeeded? → A: **No trade-off is required — ordering resolves it (FR-060a).** Commit the operational status writes first, **then** attempt the lease, and signal failure only after those writes have committed. The apparent conflict assumed that failing the invocation discards earlier writes; it does not — signalling failure does not roll back a committed write. The run is retried, the operational writes re-apply harmlessly as the idempotent per-ad overwrites FR-055's rationale already describes, and the learning write gets another attempt. Stated explicitly because the wrong ordering is the natural thing to implement and nothing previously forbade it.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Learning Never Resets (Priority: P1)

The owner has been running a low-ticket funnel for weeks. The system has watched dozens of ads and built up a picture of which hook angles and which visual patterns earn results. The owner then changes the funnel's economics, or runs a shorter manual refresh that only covers part of the account. When the owner next looks at what the system has learned, **the accumulated picture is still there, unchanged and undiminished**. Nothing that was learned has been forgotten, and nothing has been counted twice.

**Why this priority**: This is the owner's stated requirement and the load-bearing defect. Without it, every other improvement is written onto a record that erases itself. It is also the minimum viable slice: cumulative, idempotent, shrink-proof accumulation delivers the owner's core ask even before any new measure is added.

**Independent Test**: Run the same sync payload repeatedly and confirm the stored learning record after the tenth run is identical to the record after the first. Then run a sync covering a strict subset of the previous ads and confirm every stored record — including those for angles the partial sync did not touch — is unchanged or larger, never smaller.

**Acceptance Scenarios**:

1. **Given** an account whose learning record shows an angle used 12 times with 5 successes, **When** a sync runs that returns those same 12 ads with unchanged performance data, **Then** the record still shows 12 uses and 5 successes — not 24 and 10, and not 12 and 5 recomputed from scratch.
2. **Given** an account with learning recorded across four hook angles, **When** a partial refresh returns ads belonging to only one of those angles, **Then** the records for the other three angles are byte-for-byte unchanged and the touched angle's counts do not decrease.
3. **Given** an account with an established learning record, **When** the owner changes the funnel's cost target and the next sync runs, **Then** no angle's usage count and no angle's success count decreases.
4. **Given** an ad that has already contributed to an angle's record, **When** that ad appears in twenty subsequent syncs with unchanged performance data, **Then** it is counted exactly once across all twenty.

### User Story 2 - A Result, Once Earned, Stays Earned (Priority: P2)

An ad performed well against the economics that were in force when it ran. Later the owner changes those economics — a different price point, a different offer, a different funnel entirely. The ad's place in the learning record still reflects how it actually did **at the time it ran, against the target it was actually running against**. Changing today's settings does not retroactively rewrite yesterday's result. At the same time, the owner's day-to-day action list still reflects today's economics, because an ad that is too expensive under the new target is still too expensive today.

**Why this priority**: This is what makes accumulation *meaningful* rather than merely *stable*. Without a recorded evaluation context, an accumulated count is a pile of results measured against unknown and mutually incomparable yardsticks. It is P2 rather than P1 because P1 already stops the visible loss; P2 makes what survives trustworthy.

**Independent Test**: Record an ad's learning result under one cost target, change the target, re-run the sync, and confirm the ad's stored learning result and its stored evaluation context are unchanged — while confirming the same ad's day-to-day status line has moved to reflect the new target.

**Acceptance Scenarios**:

1. **Given** an ad whose learning result was sealed against a $50 target, **When** the owner lowers the target to $30 and a sync runs, **Then** the ad's sealed learning result, its sealed target, and its sealed efficiency figure are all unchanged.
2. **Given** that same ad and that same target change, **When** the owner opens the day-to-day view, **Then** the ad's current status reflects the new $30 target, because the current status is an action list, not a history.
3. **Given** an ad that is still running and gathering new data, **When** a sync brings genuinely new performance data for it, **Then** its learning result is re-evaluated — but against the target sealed on its first evaluation, never against a newer target — and the angle's totals are adjusted so the ad is still represented exactly once.
4. **Given** an ad running under a funnel whose economics cannot be resolved, **When** the sync evaluates it, **Then** its contribution is recorded as provisional — it contributes to usage and click-through learning but not to efficiency learning, and no target is recorded.
5. **Given** that provisional ad, **When** the owner completes the funnel settings weeks later and a sync runs, **Then** the ad seals against the target resolvable at that moment, gains an efficiency figure, and the account's distinct-ad count does not increase — the ad was already counted.
6. **Given** an ad whose contribution is already sealed, **When** any path attempts to re-evaluate it against a different resolvable target — a settings change, a manual refresh, or an economics version bump — **Then** the write path refuses the change and the original sealed target survives.

### User Story 3 - Winners Transfer Between Funnels (Priority: P3)

The owner proves a hook angle on a low-ticket funnel. Months later the owner launches a high-ticket funnel with completely different economics. The system does not start from zero: it still knows that angle works, it says so, and it says so more confidently when it has also seen the angle succeed in a funnel like the new one. It never withholds a proven winner just because the winner was proven somewhere else.

**Why this priority**: This is the second half of the owner's sentence — "when something works in a specific funnel, we should use that learning in different funnels." It depends on P2 having sealed a comparable efficiency figure, which is why it follows.

**Independent Test**: Build a learning record where an angle has strong evidence from one funnel type and no evidence at all from a second. Request guidance for the second funnel type and confirm the angle is still offered, and confirm that a second angle with equally strong evidence *from the requested funnel type* is ranked ahead of it.

**Acceptance Scenarios**:

1. **Given** an angle with strong evidence recorded entirely under one funnel type, **When** guidance is requested for a different funnel type, **Then** the angle is still eligible to appear among the recommended angles.
2. **Given** two angles with comparable overall evidence, one proven under the requested funnel type and one proven only elsewhere, **When** guidance is requested, **Then** the same-funnel angle ranks higher.
3. **Given** an angle proven only under a different funnel type, **When** guidance is requested, **Then** the angle is never filtered out, suppressed, or zeroed on the grounds of funnel type alone.
4. **Given** an ad whose funnel type cannot be determined, **When** it contributes to learning, **Then** it still contributes to the angle's overall totals and is recorded under an explicit unknown bucket, not silently attributed to a real funnel type.

### User Story 4 - The Owner Sees the All-Time Truth (Priority: P4)

The owner opens the "What's Working" view. The counts shown are all-time counts across every funnel the owner has ever run — not "what happened in the last refresh". The angles the system recommends when generating new creative are drawn from that same all-time record. Every number and label the owner reads is in plain language, in both English and simple Fusha Arabic, with no advertising jargon and no raw measurement values.

**Why this priority**: The reading surfaces are additive changes over the new record shape. They are last because the record must exist and be correct before it can be displayed, but the feature is not delivered until the owner can actually see the accumulated learning.

**Independent Test**: Populate a learning record spanning several funnel types and multiple syncs, then confirm both the dashboard view and the creative-guidance path report figures consistent with the all-time record, in both languages, with no jargon.

**Acceptance Scenarios**:

1. **Given** an angle with all-time usage across three separate syncs, **When** the owner opens the "What's Working" view, **Then** the usage and success counts shown are the all-time totals.
2. **Given** an account that has crossed the threshold at which the system begins steering creative generation with learned guidance, **When** a later partial sync runs, **Then** the guidance stays switched on — it can never switch back off because a refresh was incomplete.
3. **Given** an angle whose evidence spans more than one funnel type, **When** the owner views it, **Then** a plain-language line indicates the angle has worked in more than one of the owner's funnels, in the owner's language.
4. **Given** any newly introduced owner-visible text, **When** it is displayed in either supported language, **Then** it contains no advertising jargon and no raw measurement values.

### Edge Cases

- **An ad has no conversions.** No efficiency figure can be computed. The ad still contributes usage, click-through, and cost-per-thousand learning, and still contributes its win/lose mark if the engine produced one. It contributes nothing to the efficiency measure.
- **The funnel's economics cannot be resolved** (settings absent, incomplete, or not stamped with the current economics version). The contribution is recorded as PROVISIONAL — usage, click-through, and cost-per-thousand evidence count normally, no target or efficiency figure is recorded, and the ad must never be sealed against a placeholder or infinite target.
- **A provisional ad becomes sealable weeks later.** The owner completes funnel settings after several syncs have already run. Every PROVISIONAL ad still present seals on the next evaluation, against the target resolvable at that moment (FR-005d). Its usage and click-through evidence was already counted and must not be counted a second time.
- **A sealed ad is presented with a different resolvable target.** It keeps its original sealed target, sealed efficiency figure, and sealed funnel type. The write path must refuse the change rather than rely on callers not attempting it.
- **An economics version bump changes how targets are derived.** Sealed ads are unaffected — a version bump is a settings change, and FR-005c names it explicitly as a path that may not re-open a sealed contribution.
- **A single fluke conversion produces an absurd cost figure** — one conversion on high spend can yield an efficiency figure tens of times worse than target. The raw figure is preserved on the ad's own record for audit; the value folded into the angle's average is bounded so one such ad cannot dominate the angle.
- **An ad is linked to a generation for the first time after it already contributed.** Its angle and visual pattern change. Its previous contribution must be withdrawn from the old angle before the new one is added, so the ad is still represented exactly once overall.
- **A generation is deleted after its ad already contributed.** The existing system invariant is that already-learned signal stands and aggregates are not recomputed on delete. That invariant is preserved: deletion does not withdraw a contribution already made; it only prevents further contributions.
- **Two syncs for the same account overlap.** The second run cannot acquire the learning lease. A manual run tells the owner a refresh is already in progress; a scheduled run signals failure so the task infrastructure retries it with backoff. Neither writes learning concurrently with the other.
- **A sync crashes or is killed by the platform while holding the lease.** The lease expires on its own 15 minutes after acquisition. No manual intervention, no permanently locked account.
- **A lease is force-expired and taken over while its original holder is still running.** The original holder detects on its pre-commit re-verification that it no longer holds the lease and aborts its learning write entirely, leaving existing records untouched. It does not write alongside its replacement.
- **A run's lease expired and was taken over, and the run then finishes and tries to release.** Release verifies holder identity, so the stale run cannot release its successor's lease.
- **A scheduled run exhausts its retries against a persistently held lease.** Treated as deduplication rather than loss: another run was writing that account's learning throughout. The next scheduled cycle restores full coverage, and FR-020 guarantees the run that won cannot have shrunk anything.
- **A ledger read fails for part of the batch.** The learning write for those ads is abandoned and their existing contributions stand. They are never treated as uncontributed, because a read failure is missing information rather than evidence of absence.
- **The batch contains more ads than a single by-ID read can carry.** The read is chunked, and every chunk completes before any write is issued, so a partially-read ledger cannot produce a partially-applied set of contribution decisions.
- **Someone later adds a retention policy to ad performance documents.** Forbidden, with the reason recorded at the write site itself, because deleting an ad document erases its ledger entry and silently re-enables double-counting for that ad.
- **A learning record predating this feature is encountered.** It is treated as absent — it contributes zero to every reader and is replaced in full on first write, never incremented onto.
- **Meta stops returning an ad.** Its existing contribution stands. Absence is not evidence of failure and must never reduce a count.
- **An angle is seen for the very first time.** Accumulation onto a non-existent record must produce the same result as accumulation onto an empty one.

*Added by Amendments 1 and 2. One line per case; the handling lives in the requirement named, not here.*

- **A creative is split across two hash groups that never merge.** Neither group carries a link, so there is nothing to merge on — FR-074b's stated limitation.
- **A hashless row carries a propagated link and its source group is later re-linked.** The row does not move with the group and its attribution is frozen — FR-074e's stated limitation.
- **A creative's rows hold mixed PROVISIONAL and SEALED states during the settings gap.** FR-036c.
- **A row first appears in a later sync and inherits the creative's sealed target** rather than sealing against the target current at its own first sight. FR-012a.
- **A creative reaches its fifth conversion on a different ad row from the earlier four.** FR-077, SC-033.
- **A still-open day is re-observed with a lower figure.** FR-083 (upward-only).
- **The seventh consecutive missed sync**, where day loss begins. FR-086.
- **A parent-paused ad never seals via condition (b).** FR-085.
- **Two runs for one account arrive by different routes** — inline and Cloud Tasks worker. FR-054c.
- **Two already-sealed creatives merge while carrying different sealed targets.** The earliest survives. FR-012a (as rephrased), FR-074b.
- **A merge in which both halves had already contributed an efficiency figure.** Withdraw both, recompute over the union, add one. FR-013a, FR-087(ii).
- **A creative that has already contributed its efficiency figure is re-attributed.** The figure moves unchanged; it is not recomputed. FR-087(i).
- **Meta returns no daily row for a day that falls inside an observed window.** The ad did not deliver; the day is not observed, not zero, and this is **not** a gap. FR-085a, FR-086a.
- **A run cannot acquire the learning lease partway through an otherwise successful sync.** Operational writes have already committed; the run signals failure and is retried. FR-060a.

## Requirements *(mandatory)*

### A. Sealed Evaluation Context (per ad)

- **FR-001**: The system MUST record, on each ad's performance record, the cost target that was in force at the moment the ad's learning result was determined.
- **FR-002**: The system MUST record an **efficiency figure** expressing realised cost per result relative to the sealed target. It is **stored on each ad row's performance record** (the ledger's storage location, FR-016) and **computed at the creative** (the unit of evidence, FR-073) per FR-002a.
- **FR-002a**: A creative's efficiency figure MUST be computed by **aggregate-then-divide**: sum realised cost and sum results across **all** the creative's rows (FR-074g), then divide the summed cost by the summed results to obtain one realised cost per result, then divide that by the creative's single sealed target (FR-012a). **Divide-then-average — computing a ratio per row and averaging the ratios — is forbidden.**
  - *Justification*: the two produce different numbers, and divide-then-average gives a one-result placement the same weight as a fifty-result one. Across a creative spanning 55 ad rows that is not a rounding difference: a single freak row can move the creative's figure substantially, which is the same fluke-domination problem FR-038 bounds at the aggregate and which must not be re-introduced one level down. Aggregate-then-divide is also what FR-021's **raw sums and counts** exist for — they are stored precisely so a contribution can be added or withdrawn exactly — and it is what the efficiency eligibility rule (FR-077) already presumes when it counts *"combined conversions across all placements"*.
  - *Consequence for the sealed target*: aggregate-then-divide requires a **single** denominator, which is exactly why FR-012a fixes one sealed target per creative. The two requirements are load-bearing for each other.
- **FR-003**: The efficiency figure MUST be defined as **realised cost per result divided by the sealed target**, stored raw and unbounded. A value of 1.0 means the creative landed exactly on target; 0.6 means it came in 40% under target; values above 1.0 mean it exceeded target. Lower is better.
  - *Justification*: this formula is lossless, directly interpretable in the owner's own framing ("an ad at 0.6× its own target"), and target-normalised — so 0.6 on a $12 lead funnel and 0.6 on a $200 product funnel are literally the same number, which is the cross-funnel comparability this feature exists to create. The bounded alternative `min(cost, target) / target` was considered and rejected: it caps at 1.0 and therefore erases the entire distinction between "hit target" and "beat target threefold", which is precisely the winner signal the owner wants to carry between funnels.
- **FR-004**: The system MUST record, on each ad's performance record, the funnel type in force when its learning result was sealed, or an explicit unknown marker when it cannot be determined.
- **FR-005**: When the cost target cannot be resolved, the system MUST NOT seal a placeholder, a zero, or an unbounded stand-in for it. Instead, the ad's contribution is marked **PROVISIONAL** per FR-005a. An unresolvable target is an unfinished evaluation, not a sealed decision.
- **FR-005a**: Every learning contribution MUST carry exactly one of two states:
  - **PROVISIONAL** — no cost target was resolvable at evaluation time. The ad contributes usage, click-through, and cost-per-thousand evidence normally, and contributes its win/lose mark if the engine produced one. It carries no sealed target and no efficiency figure.
  - **SEALED** — a cost target was resolvable and has been recorded, together with the efficiency figure and funnel type derived from it.
- **FR-005b**: The transition PROVISIONAL → SEALED MUST occur at the first evaluation at which a cost target is resolvable.
- **FR-005c**: The transition MUST be **one-way, and enforced in code rather than by convention**. Once a contribution is SEALED, no code path may return it to PROVISIONAL or alter its sealed target — not a funnel settings change, not a re-sync, not a manual refresh, not an economics version bump. The enforcement MUST be a guard in the write path, not a comment or a caller-side discipline.
  - **EXPLICIT CARVE-OUT (Amendment 2): the first write of a creative's efficiency figure under FR-077 is NOT a re-opening and MUST be permitted through this guard.** Without this carve-out the guard forbids the very write FR-077 requires, since that write necessarily lands on an already-SEALED contribution.
  - *What the carve-out does and does not permit*: it permits the efficiency figure to go from **not-yet-determined** to **a number, exactly once** (FR-079). It does **not** permit the sealed target, the sealed funnel type, or the moment of sealing to change; it does **not** permit a second efficiency write; and it does **not** permit a return to PROVISIONAL. The guard MUST therefore test the specific transition, not merely the SEALED flag — a guard written as "reject any write to a SEALED contribution" is too coarse and would block FR-077; a guard written as "allow any write to a SEALED contribution" is too loose and would readmit everything FR-005c exists to forbid.
- **FR-005d**: Sealing MUST use the target resolvable **at the moment of sealing**, not the target that was in force when the ad ran.
  - *Known and accepted imprecision*: an ad first seen in week 1 with no settings, and sealed in week 3 when settings are completed, seals against week 3's target even though its spend was incurred in week 1. This is deliberate. The alternative — reconstructing week 1's target — is **impossible**, because no settings history is retained (investigation §2.3 established that only the current settings document exists). The trade is that an approximate efficiency figure beats no efficiency figure, and the approximation is bounded to the window between an ad's first appearance and the completion of funnel settings, which is a one-time setup gap rather than an ongoing condition.
- **FR-005e**: **Sealing a target and contributing an efficiency figure are two separate events, and MUST NOT be conflated.** Amendment 2 requires a creative that is sealed against a target to nevertheless **withhold** its efficiency contribution until FR-077's eligibility is met. The two-state machine below has no name for that condition, so the separation is stated here rather than encoded as a third state:
  - **Sealing the target** fixes the evaluation context (target, funnel type, moment). It happens at the first evaluation at which a target is resolvable (FR-005b) and is one-way (FR-005c).
  - **Contributing the efficiency figure** folds a number into the angle and pattern records. It happens when FR-077's eligibility is met, which may be **later, in a different sync, or never**.
  - *Why no third state was added*: the states in FR-005a describe whether an **evaluation context** exists. Eligibility to contribute a figure is not a property of the context — it is a property of the accumulated conversions. Encoding it as a state would make the machine two-dimensional and put FR-005c's one-way guarantee at risk for no gain. A SEALED contribution whose figure has not yet been contributed is simply a SEALED contribution; the ledger records which of the two events has occurred.
  - *Relationship to FR-006*: FR-006's zero-result case is **not** a withheld contribution. There the target is sealed and the figure is recorded as **explicitly absent** — a final answer. Under FR-077 a withheld figure is **not yet determined**. Absent and not-yet-determined are different, and readers MUST distinguish them: the first never becomes a number, the second may.
- **FR-006**: When the ad has no results in the measurement window, the system MUST record the efficiency figure as explicitly absent while still sealing the target if one was resolvable. Such a contribution is SEALED, not PROVISIONAL: the target was known, the ad simply produced nothing to measure against it.
- **FR-007**: The state, the sealed context, and the learning result MUST be written in the same operation, so an ad can never carry a result without the context and state that produced it.

### B. Freezing and Re-evaluation

- **FR-008**: The system MUST distinguish two separate things carried on an ad's record: the **operational status** the owner acts on today, and the **sealed learning result** the accumulated record counts.
- **FR-009**: The operational status MUST continue to be recomputed on every sync against the current economics, unchanged from present behaviour. It is an action list, and it must stay current.
- **FR-010**: The sealed learning result and its sealed context MUST NOT be rewritten because the funnel's economics changed. A change to settings alone is **never** a material change.
- **FR-011**: The system MUST re-evaluate an ad row's sealed learning result when, and only when, one of the following material changes occurs. **Scope (Amendment 1): detection is row-scoped, effect is creative-scoped.** Each trigger is detected on the row whose data changed, but the resulting adjustment is applied so that the *creative* remains represented exactly once (FR-013).
  - *Per-trigger scope*: **(a)** is **row-scoped in detection** — each ad row carries its own measured performance, and one placement's metrics moving says nothing about its siblings. **(b)** is **creative-scoped in effect** — FR-074a propagates a manual re-link across the whole hash group, so an attribution change on one row re-attributes every row of that creative. **(c)** is **creative-scoped**, because target resolvability is an account-level condition, not a per-row one (FR-005d, FR-036c).
  - **(a) The ad's own measured performance changed** — the measurement inputs the result was derived from differ from those recorded with the sealed result. A still-running ad continues to refine its own record as real data arrives.
    - **NARROWED BY AMENDMENT 2. This trigger applies to the TARGET-INDEPENDENT measures ONLY** — usage, click-through, and cost-per-thousand — **and MUST NOT re-evaluate the efficiency figure.** The efficiency figure is contributed exactly once under FR-077 and is never revised by a performance change.
    - *Why it is narrowed rather than deleted*: this trigger is also what keeps click-through and cost-per-thousand current through FR-017's withdraw-then-add, and FR-024 requires those measures to keep their meaning while widening their window to all time. Deleting FR-011(a) outright would freeze them at first contribution, which is the opposite of what FR-024 asks for. It is therefore narrowed in *scope of measures*, not removed.
    - *What the narrowing buys*: a running creative's efficiency is still moving, so contributing it and correcting it on every sync is a live feed, not learning. FR-051d's volume table is corrected accordingly.
  - **(b) The ad's creative attribution changed** — the ad became linked to a generation, or its link changed, altering which angle or which visual pattern it belongs to.
  - **(c) A PROVISIONAL contribution became sealable** — a cost target is resolvable for the first time (FR-005b). This is not an exception to FR-010: there is no sealed context here to protect, only an unfinished one to complete. It can occur at most once per ad, and FR-005c forbids the reverse.
- **FR-012**: On re-evaluation under FR-011(a), the system MUST evaluate against the **sealed** target, never the current one. The sealed target is fixed at the moment a contribution is sealed and never changes for its life. A SEALED contribution presented with a different resolvable target MUST retain its original sealed target — this is a required test, not merely an intended behaviour.
- **FR-012a**: **A creative MUST carry exactly one sealed target across all of its rows.** The target sealed by the **earliest-sealing row among all rows now belonging to the creative** becomes the creative's sealed target, and every row of that creative — including rows that first appear in later syncs, and rows that join through a merge — inherits it rather than sealing independently against whatever target is resolvable at its own first sight.
  - **This phrasing is what makes FR-012a merge-safe, and the wording is deliberate.** An earlier version read *"the first row of that creative to seal"*, which is well-defined for a creative whose membership never changes and undefined the moment FR-074b merges two groups that have **each already sealed**, possibly against different targets sealed at different times — reproducing exactly the multi-target condition this requirement exists to forbid. Saying *"among all rows now belonging to the creative"* makes a merge simply widen the set the existing rule ranges over, so **the earliest sealed target survives** and no separate merge rule is needed.
  - *Why this rule is required rather than assumed*: FR-001 writes the sealed target on each ad row's record, and FR-005d seals against the target resolvable **at the moment of sealing**. Rows of one creative do not necessarily seal at the same moment — a new placement of an existing creative first appears in a later sync — and the account's cost target can change in between. Without this rule, one creative could hold two or more different sealed targets, and its efficiency figure (FR-002, FR-003) would be a ratio against no single denominator. Since the creative is the unit of evidence (FR-073), its sealed context must be single-valued too.
  - *Consistency with FR-005c*: inheritance is not a re-opening. The creative's sealed target is written once and never revised; a later row adopts it rather than creating a competing one, so the one-way guarantee is strengthened, not weakened.
  - *Consistency with FR-005d's accepted imprecision*: this widens that imprecision from "an ad seals against the target in force when it sealed" to "a creative seals against the target in force when its first row sealed". The trade is the same one FR-005d already accepted, and the alternative — a creative with several targets — is worse than an approximate single one.
  - *Ties are harmless and MUST NOT be broken by ordering machinery*: "the first row to seal" is under-determined when several rows of a creative seal in the same sync, because evaluation order within a sync is arbitrary. This carries **no information and needs none**. Target resolvability is an **account-level** condition (FR-005d), so every row sealing in a single evaluation resolves the **same** target — whichever is called first, the creative's sealed context is identical. Implementations MUST NOT introduce ordering, sequencing, or tie-breaking machinery to resolve a distinction that has no observable consequence. The rule only bites **across** syncs, where the account target may genuinely have changed in between.
- **FR-013**: On re-evaluation under FR-011(b), the system MUST withdraw the **creative's** previous contribution from the angle and visual pattern it was previously attributed to before adding its new contribution, so the **creative** remains represented exactly once in total.
  - *What happens when one row of a multi-row creative changes attribution and its siblings do not*: **this case does not arise as a partial re-attribution, and the spec says so rather than leaving it inferable.** FR-074a propagates a manual link across the whole hash group, so a re-link on any single row re-attributes **every** row of that creative in the same pass. The withdraw-then-add therefore operates on the creative as a whole: one withdrawal from the old angle and pattern, one addition to the new. There is never a state in which some rows of a creative count toward one angle and the rest toward another.
  - *The one residual case*: a row that leaves the group entirely — its `imageHash` changes such that it no longer groups with its siblings and it carries no link of its own — is not a re-attribution of the creative but the appearance of a **new** creative (FR-074, FR-074b). It is added, not swapped, and the original creative's contribution is untouched.
  - **FR-013a**: **A merge (FR-074b) requires the two-withdrawals-one-addition shape, which the one-for-one wording above does not cover.** When two groups that have each already contributed are found to be one creative, the system MUST **withdraw both contributions**, **recompute over the union** against the surviving sealed target (FR-012a, FR-087(ii)), and **add exactly one**. The merged creative MUST end up represented **once**, not twice and not zero times.
    - *Ordering*: both withdrawals MUST complete before the addition, so no intermediate state counts the creative twice. This is the same before-any-write discipline FR-069 already requires of chunked reads.
    - *Where only one half had contributed*: withdraw that one, recompute over the union, add one. Where **neither** had, no withdrawal is needed and the merged creative contributes when FR-077 makes it eligible over the union — which it may reach sooner than either half did alone (FR-077a).
- **FR-014**: Loss of creative metadata (the delete cascade) MUST NOT withdraw a contribution already made. It MUST only prevent further contribution. This preserves the existing invariant that already-learned signal stands.
  - *Scope*: **creative-scoped in effect, row-scoped in mechanism.** The cascade marks ad documents by `generationId`, so it reaches every row of the affected creative at once; a creative is never left half-cascaded. The already-made contribution that stands is the **creative's**, counted once.

### B2. The Unit of Evidence: The Creative, Not the Ad Row

*Added by Amendment 1 (post-approval). This section re-bases the whole specification: wherever the document previously counted **ads**, it now counts **creatives**. The ad document remains the storage location of the contribution ledger — that is unchanged — but it is no longer the unit of evidence.*

**The contradiction this overturns.** The module header of `functions/src/learningAggregates.ts:17` states the current rule as: *"Same generationId in 2 ad sets → separate records per context."* That rule is what this section replaces. It was not modified by Phase 970 and is still live in the code, so it MUST be named here explicitly — a future reader finding it must recognise it as superseded rather than binding.

- **FR-073**: The **creative** MUST be the unit of evidence for all learning. One creative contributes exactly once to any angle record or visual-pattern record, no matter how many Meta ad rows carry it.
  - *Justification*: the same creative runs across multiple ad sets and campaigns, and Meta assigns each placement its own ad id. Production confirms the fan-out: for account `act_995888422231015`, **383 ad rows group into 52 distinct creatives (7.37:1), with the largest creative spanning 55 rows**; across both connected accounts, **1008 rows group into 146 creatives (6.90:1)**. Treating each row as independent evidence splits one creative's evidence across many records and lets placements of the same image contradict one another inside a single aggregate.
  - The **storage location of the ledger is unchanged**: the contribution ledger entry stays on the ad performance document (FR-016, Key Entities), because that is the document the sync already reads by ID. Unit of evidence and storage location are separate concerns and MUST NOT be conflated.
- **FR-074**: Creatives MUST be identified by grouping ad rows on **`imageHash`**. Where any row in a hash group carries a generation link, **every** row in that group MUST resolve to that same `generationId`. The creative's evidence is the aggregate over all rows in the group.
  - **FR-074a**: Where rows within one hash group carry **different** generation links, **manual attribution MUST take precedence over automatic**. This is not a new rule — it is the precedence the sync already enforces at `functions/src/metaSync/shared.ts:864-869`, where a stored `matchType` of `"manual"` or `"auto_hash"` locks the row's link against re-derivation.
  - *Why the naive fallback is insufficient*: a rule of "group by `generationId` where present, falling back to `imageHash`" splits one creative into two groups the moment manual linking is used. Manual linking targets exactly one ad document (`functions/src/linkUnmatchedAd.ts:121-125`, whose ref is `.collection("adPerformance").doc(req.adId)`), and the sync locks that link indefinitely (`shared.ts:864-869`). Linking a single row of the 55-row creative therefore yields a permanent 1-row group and a permanent 54-row group, with the evidence-bearing majority reading as unlinked and never healing. That is precisely the evidence-splitting failure this amendment exists to prevent, occurring inside the amendment's own key. Grouping on `imageHash` first and propagating the link across the group closes it.
  - **FR-074b**: After hash grouping and link propagation, **any two groups that resolve to the same `generationId` MUST merge into a single creative.** Grouping on `imageHash` alone is necessary but not sufficient. The merged creative's sealed target is the earliest of those held by its constituent rows (FR-012a); its efficiency figure is **recomputed over the union** (FR-087(ii)); and its aggregate contributions are reconciled by FR-013a.
    - *Justification*: perceptual matching is **distance-based, not exact**. `matchAdCreative` (`functions/src/metaSync/shared.ts:407`) accepts any candidate within a Hamming distance of **10** (`shared.ts:797`), and the accepted distance is stored per row as `matchDistance`. So one creative can legitimately produce **more than one** `imageHash` — a re-upload, a re-encode, or a platform-side re-compression shifts the hash a few bits while still matching the same generation well inside threshold. Without this merge step, one creative becomes two groups and is counted twice: the same evidence-splitting failure FR-073 exists to prevent, reached by a different route than the one FR-074a closes.
    - *Not observable in production today*: only **one** `generationId` is linked at all across 1008 rows, and it maps to exactly **one** `imageHash` (`f5e9a98dadad8d9d`), with all five of its rows at `matchDistance: 1`. **Zero** generations map to more than one hash. The case therefore **cannot be sampled and MUST be constructed in fixtures**, exactly as the Assumptions already require for the linked path generally. Distance 1 out of a permitted 10 also shows how much headroom the threshold leaves for a second hash to arrive.
    - **STATED LIMITATION — this merge requires a link, and most rows do not have one.** FR-074b merges on a shared `generationId`. Where **neither** group carries a link, there is nothing to merge on, and **two hash groups that are genuinely one creative remain two creatives permanently. Nothing in this feature detects it.**
      - *Scale of the gap*: on `act_995888422231015` this is **the entire account** — 0 of 383 rows are linked, and that account supplies 52 of the dataset's 146 creatives. It is not an edge case there; it is the normal condition.
      - *Direction of the error*: **inflation.** A split creative is counted twice, so the distinct-creative count runs **high**, and FR-034, FR-034a and FR-037 therefore fire **earlier** than the deliberately-seven-times-harder bar recorded in FR-034's justification. The gates are conservative by design and this erosion works against that design, so it must not be discovered later as a surprise.
      - *Why near-hash clustering is NOT specified here*: clustering rows against **each other** by distance is a different operation from matching a row against the fingerprint index. It is **non-transitive** — A within 10 of B and B within 10 of C does not put A within 10 of C — so it has no well-defined grouping without further choices, and it risks merging genuinely distinct creatives, which is a worse failure than splitting one. That is a design decision, not a specification correction, and it is deliberately **not** taken here.
      - *Cross-reference*: recorded against FR-034's PROVISIONAL review trigger as a reason the threshold may behave differently in practice from the calibration argument that justified keeping it.
  - *Why `metaAdId` cannot be the key*: it is assigned from `ad.ad_id` at `functions/src/metaSync/orchestrator.ts:455`, so it is the **per-row** Meta identity by construction. (This assignment was relocated from `index.ts:3931` by Phase 970, which moved the legacy user-level sync body into the orchestrator as "LEG A" — it was **relocated, not removed**, and the old citation must not be read as evidence of removed behaviour.) It is also **absent, not null**: 0 of 1008 workspace-scoped ad rows carry the field at all — `AdDoc` (`shared.ts:170-211`) has no such member — and 0 of 58 `creativeDeployments` records carry a non-null value.
- **FR-074c**: An ad row carrying a `generationId` but **no** `imageHash` MUST be attributed to the creative of that `generationId`, joining the group already resolving to it. Where no other row resolves to that `generationId`, it forms its own single-member group, and that group **does contribute** — it is a full member of the learning record, not a bookkeeping placeholder.
  - *This is distinct from FR-075 and MUST NOT be read as the same case.* FR-075's group cannot contribute because `isEligibleForLearning` fails without a `generationId`. Here `isEligibleForLearning` **passes** — the row has a link, and every angle and visual-pattern field is readable from the matched generation. Missing hash costs the row nothing except the ability to be grouped by hash, and the `generationId` supplies grouping directly.
  - *That the combination is reachable, verified*: `imageHash` is written **independently of match success** — `result.imageHash = hash` (`shared.ts:796`) executes **before** `matchAdCreative` (`shared.ts:797`) — so it is null only when the ad has no image URL (`shared.ts:792`) or the download/hash throws (`shared.ts:794-802`). Two concrete routes then produce a linked row with no hash: (a) `linkUnmatchedAd.ts:146-155` creates a pre-sync manual-link record carrying `generationId` and `matchType: "manual"` with **no `imageHash` field at all**; (b) an already-linked row whose image download fails on a later sync has `imageHash: match?.imageHash ?? null` (`shared.ts:1015`) written under `{ merge: true }` (`shared.ts:1190`), which writes an explicit null, while the precedence lock (`shared.ts:864-869`) preserves its `generationId`. A previously-hashed linked row can therefore **lose** its hash.
  - *Not present in production today*: of 1008 rows, **5** carry both keys, **1003** carry a hash and no link, and **0** carry a link with no hash. Reachable, not yet realised — so this too must be constructed in fixtures.
  - *Precision note on the guard commonly cited here*: `shared.ts:430` skips a **malformed fingerprint-index entry**, not the ad's own hash. It protects matching from one bad stored fingerprint; it is not the route by which a row ends up hashless. The routes are the two above.
- **FR-074d**: **The creative grouping is derived per sync; the resolved `generationId` MUST be persisted on the row.** These are two separate statements and both are required.
  - *Derived*: the creative itself is never stored as a document. Groups are recomputed from the current rows on every sync (Key Entities, *Creative*), so a merge (FR-074b) or a re-link (FR-074a) takes effect immediately without migrating anything.
  - *Persisted*: when FR-074 or FR-074b resolves a row to a `generationId` the row did not itself carry, that `generationId` **MUST be written back to the row**.
  - *Why persistence is required, not optional*: if the link were derived only, a row that loses its `imageHash` would leave every hash group, carry no link of its own, and fall to FR-075 — the group that **cannot contribute**. A row that had been contributing would silently stop. That route is real, not hypothetical: `imageHash: match?.imageHash ?? null` (`shared.ts:1015`) writes an explicit null under `{ merge: true }` (`shared.ts:1190`) whenever a later download fails. Silently dropping that row's contribution would violate **FR-014**, which permits loss of metadata to prevent *further* contribution but never to withdraw one already made, and would sit against **FR-020**, since a row falling out of its own group is not evidence of anything. Persistence makes the attribution survive the hash.
  - **FR-074e**: A written-back link MUST be **distinguishable from a directly-matched one**, and MUST NOT inherit the authority of one. The stored match provenance MUST record three distinct origins, and precedence between them is strict:
    1. **manual** — set by the owner (`linkUnmatchedAd.ts:134-142`). Highest authority. Never overridden by anything below it.
    2. **direct automatic** — this row's own image matched the fingerprint index within threshold (`matchAdCreative`, `shared.ts:407`).
    3. **propagated** — this row carries no match of its own and inherited the link from its group (FR-074, FR-074b). **Lowest authority.**
    - *Why this is required*: the precedence lock at `shared.ts:864-869` locks any row whose stored `matchType` is `"manual"` or `"auto_hash"` against re-derivation. If a propagated link were written back under either of those values it would be **indistinguishable from an original**, and the lock would make an inferred attribution permanent — a wrong propagation could never be corrected by a later direct match. A propagated link MUST therefore remain **re-derivable**: it survives to keep the row contributing, and it yields to a direct or manual match the moment one appears — **for any row that still carries an `imageHash`**. For a hashless row no such match can appear, and the qualification is stated in the limitation below rather than left implied.
    - *Reconciliation with FR-014 and FR-020, stated explicitly*: a row that loses its hash keeps its propagated link, keeps its place in the creative, and keeps contributing. Nothing is withdrawn, no count decreases, and the loss prevents only the row's ability to be **re**-grouped by hash — which is exactly the "prevent further, never withdraw" shape FR-014 requires.
    - **STATED LIMITATION — re-derivability does NOT reach a hashless row.** The yields-to-a-better-match rule above holds only for a row that can still be *evaluated*. A row with **no** `imageHash` has nothing to match against the fingerprint index, so no direct match can ever appear for it; and no owner will manually link a row that already reads as linked. **Its propagated attribution is therefore frozen and unverifiable for the life of the row.**
      - *Trigger sequence*: a row in a group resolving to `G` loses its hash (`shared.ts:1015` writing an explicit null under `{ merge: true }` at `shared.ts:1190`) and is written back with a propagated link to `G`. A sibling is later manually re-linked to `G'`. FR-074a moves the whole hash group to `G'` — but the hashless row is **no longer in any hash group**, so it does not move. Under FR-074c it attaches to `G`'s creative; where no other row resolves to `G`, it becomes **its own contributing creative, attributed to a generation nothing else uses**.
      - *Direction of the error*: **mis-attribution plus inflation** — the row's evidence lands on the wrong angle and pattern, and a spurious extra creative is counted. Both work against the conservative intent of FR-034 / FR-034a / FR-037, as FR-074b's limitation does.
      - *Bound*: the frequency of a **linked** row losing its hash, which is a creative-image download failure on a row that had previously matched. The FR-076 provenance breakdown makes exactly this visible — a rising propagated-only count with no corresponding rise in direct matches is the observable trace of this limitation accruing.
      - *Not fixable within this feature*: correcting the row would require placing it back in the group it must be revalidated against, and the key for doing so is the very thing it lost. Recorded as a limitation rather than papered over, in the shape FR-074b's limitation and FR-075 already model.
- **FR-074f**: Link provenance (FR-074e) MUST be stored in a **NEW FIELD SEPARATE FROM `matchType`**. `matchType`'s existing values (`"auto_hash"`, `"manual"`, `null`) and their meanings MUST NOT change, and no new value may be added to it.
  - *The decision, and why it is recorded rather than left to the implementer*: both options are defensible in the abstract — a new `matchType` value is simpler to write; a separate field is the weaker change. The separate field is chosen on evidence.
  - *Evidence 1 — `matchType` has more readers than this specification has ever enumerated.* FR-072 names three behaviours. The field is in fact branched on at, among others, `functions/src/getTopWinners.ts:79` and `:185`, `functions/src/learningAggregates.ts:120`, and `functions/src/whatsWorkingDashboard.ts:412`, `:569` and `:719`. A new enum value would change what **all** of them see, including two surfaces this feature does not otherwise touch. Most sharply, `whatsWorkingDashboard.ts:719` builds the owner-facing "needs linking" list by filtering `matchType` `=== null`: a propagated row carrying a new enum value would **silently disappear from that list**, hiding from the owner precisely the rows whose attribution is least certain.
  - *Evidence 2 — the separate field gives FR-074e's re-derivability for free.* The precedence lock (`shared.ts:864-869`) fires only when the stored `matchType` is `"manual"` or `"auto_hash"`. A propagated-only row keeps `matchType` `null`, so the lock does not fire and the row is re-matched on every sync — which **is** the re-derivability FR-074e requires, obtained from existing behaviour rather than from a new exclusion branch that a later refactor could drop.
  - *Consequence that MUST be handled, stated rather than discovered*: learning eligibility is currently a **per-row** predicate that rejects a null `matchType` (`isEligibleForLearning`, `functions/src/learningAggregates.ts:119-124`; the same test exists at `getTopWinners.ts:79`). With provenance in a separate field, a propagated-only row has `matchType` `null` and would be rejected — defeating the purpose of persisting the link at all (FR-074d). **Eligibility MUST therefore be evaluated per creative (FR-073), not per row**, and a creative whose link is propagated is eligible on the same terms as one whose link is direct. The *criteria* are unchanged — a resolvable generation, available metadata, a resolvable angle or pattern — only the **unit they are evaluated over** changes, which is Amendment 1's whole subject. The derivation is FR-074g.
- **FR-074g**: **The per-creative eligibility rule MUST be derived from its rows as follows**, stated explicitly in the manner of FR-036c rather than left to the implementer:
  - **Eligibility is ANY-ROW.** A creative is eligible for learning when **at least one** of its rows satisfies the criteria. An all-rows rule is forbidden: a propagated-only row carries a null `matchType` (FR-074f) and fails the per-row predicate individually, so an all-rows rule would make **every creative containing a propagated row ineligible** — defeating FR-074d's persistence entirely and inverting its purpose.
    - *Why any-row is safe here, and not merely convenient*: **a propagated link cannot exist unless at least one row in its group carries a real link.** Propagation has no source otherwise — FR-074 and FR-074b both propagate *from* a row that matched directly or was linked manually. So an eligible creative always contains at least one directly-matched or manually-linked row, and any-row can never admit a creative whose attribution rests on nothing.
  - **Aggregation is ALL-ROWS.** Once a creative is eligible, the measured values of **every** row in it aggregate into its contribution, not only those of its individually-eligible rows. An eligible-rows-only rule would make propagation achieve nothing: the propagated rows are exactly the placements whose evidence FR-073 exists to consolidate, and excluding them would return the record to counting one placement per creative.
  - *Interaction with the delete cascade — verified, and FR-014 is not weakened.* The cascade queries `.where("generationId", "==", generationId)` (`functions/src/generationDeleteCascade.ts:70-72`) and marks every matching row, so it reaches **every** row of a creative at once and a creative is never half-cascaded. Any-row eligibility therefore cannot leave a cascaded creative eligible through an unmarked row.
    - *And this depends on FR-074d.* Because the propagated `generationId` is **persisted** on the row, the cascade's equality query matches propagated rows too. Had the link been derived only, propagated rows would carry no stored `generationId`, the cascade query would miss them, and a creative **would** be half-cascaded. FR-074d's persistence is therefore load-bearing for FR-014, not only for contribution continuity — recorded here because the dependency is not obvious from either requirement alone.
- **FR-075**: An ad row carrying neither a `generationId` nor an `imageHash` MUST form its own single-member group.
  - *Stated limitation, deliberately not glossed over*: such a group **cannot contribute to any angle record or any visual-pattern record**. `isEligibleForLearning` (`functions/src/learningAggregates.ts:119-124`) returns false without a non-null `generationId`, and both aggregators call it first; and `hookAngle`, `layoutTemplate`, `artDirection` and `universe` are all read exclusively from the matched generation document. An unlinked group can be counted and logged, but it cannot become evidence. This requirement therefore describes a **bookkeeping** group, not a contributing one, and the spec says so rather than implying a contribution that cannot occur.
- **FR-076**: The per-sync summary line MUST report contributions **broken down by link provenance** (FR-074e), never as a single total. Four counts, all emitted on every sync including when zero:
  1. contributions from rows with a **direct automatic** match;
  2. contributions from rows with a **manual** link;
  3. contributions from rows carrying a **propagated** link only;
  4. contributions from rows resolving to **no** generation.
  - *Justification, and why a single total would be actively misleading*: this is a **monitoring** requirement, not an accounting line. **Direct-match volume is the quantity that actually tracks matching health** — it is the only one of the four that reflects perceptual matching working. Propagation (FR-074d) writes a resolved `generationId` back to rows that never earned one, so a 55-row group in which **one** row matched directly would report **zero** unlinked contributions. A single total would show near-perfect matching on the strength of one real match, and would keep showing it while direct matching degraded, for as long as one row per group still matched. **The degradation signature is a falling direct count against a rising propagated count**, and only the breakdown makes it visible. Monitoring that improves when nothing improved is worse than no monitoring.
  - *Testable*: seed a sync with a known number of rows of each provenance and assert each of the four emitted counts equals its seeded value. The counts are added to the list in FR-051b.
  - *Current baseline, against the four-way shape*: **5 direct, 0 manual, 0 propagated, 1003 unlinked** (of 1008 rows). Account `act_995888422231015` contributes **0 direct, 0 manual, 0 propagated, 383 unlinked** — every row resolves through the `imageHash` path and the `generationId` branch of FR-074 is currently **inert** there. This is the starting condition the breakdown must make visible, and the number to watch is the **5**.

*Evidence note*: for the two observed syncs, the ads Meta returned equalled the ad documents stored (383/383 and 625/625). **This is a property of those two syncs, not an invariant** — `shared.ts:848` (`if (!windows) continue`) skips any ad whose insights fetch failed, and a sync with such failures would store fewer rows than it fetched.

### B3. Efficiency Contributes Exactly Once

*Added by Amendment 2 (post-approval). Separates **sealing a target** from **contributing an efficiency figure**, and makes the second happen once, when a creative's numbers are final.*

- **FR-077**: A creative becomes eligible to contribute its efficiency figure when **either**:
  - **(a)** it reaches **5 combined conversions across all its placements** (all rows, FR-074g), **or**
  - **(b)** it has **stopped running** and carries **at least 1** combined conversion.
  - **Zero conversions never contributes an efficiency figure**, under either condition. This is FR-006's case and stays FR-006's case.
  - *Justification for the threshold of 5*: at **2** conversions one lucky sale halves the apparent cost per result. At **5** an outlier moves it roughly 20%, which is tolerable against a bound already set at 3.0 (FR-038). At **10** the data is cleaner, but almost nothing on a Gulf coaching account would ever qualify, and a gate nothing passes is a gate that switches the measure off. 5 is the point at which the figure is worth recording and still reachable.
- **FR-077a**: **A split creative splits its conversions too, and the two errors run in opposite directions. This MUST be recorded where the threshold is defined.**
  - FR-074b's limitation means two unlinked hash groups that are genuinely one creative stay two creatives, and nothing detects it. That was recorded there as **inflation** of the creative count, making FR-034 / FR-034a / FR-037 fire **earlier** than intended.
  - The same split has the **opposite** effect here: the creative's conversions divide between the halves, so a creative split in two may reach **5 in neither half** where the whole would have cleared it comfortably — and its efficiency figure is then **never contributed at all**.
  - **So one cause produces two errors in opposite directions: usage counts are inflated while efficiency contribution is suppressed.** They do not cancel; they degrade different halves of the record. An account can therefore activate guidance early (on inflated usage) and simultaneously have efficiency stay switched off far longer than the stacked-gate arithmetic in FR-037 predicts.
  - *Observability*: FR-076's provenance breakdown is the only signal that this is happening — a low direct-match count is the precondition for splitting, since FR-074b's merge requires a link.
- **FR-078**: Before a creative is eligible under FR-077, it **MUST still contribute usage and click-through**. Only the efficiency figure waits.
  - *Note on what this depends on*: those measures do **not** accumulate today — each sync rebuilds them. FR-024's widening from "the last sync" to "all time" is what makes this sentence true, so FR-078 is a statement about the system **after** this feature, not a description of current behaviour.
- **FR-079**: Once contributed, a creative's efficiency figure is **written once and never revised**. No performance change, no later conversion, and no subsequent sync may alter it. **The one case in which the number legitimately changes is a change to the creative's set of rows — see FR-087, the recomputation rule.** A re-attribution is not such a case.
  - *Consequence, stated*: a creative that contributes at exactly 5 conversions and later reaches 500 keeps the figure computed at 5. This is deliberate — the alternative is the live feed FR-011(a)'s narrowing exists to stop — and it is the reason the threshold is 5 rather than 2.
- **FR-080**: Withdraw-then-add for the efficiency figure survives **only** for attribution changes (FR-011(b) / FR-013) and for merges (FR-074b), both of which are identity corrections rather than re-measurements. It MUST NOT be triggered by a measured-performance change. **Whether the figure is recomputed or carried across during the move is decided by FR-087, not here** — this requirement governs the move, not the number.

#### Both conditions are AVAILABLE, not blocked

- **FR-081**: Condition (a)'s conversion total MUST be accumulated **per day** from the seven-day daily insights the sync **already receives**. No new Graph API call is required.
  - *Evidence*: `fetchAdInsights7dDaily` (`functions/src/metaGraph.ts:389-396`) sends `time_increment: 1`, so Meta returns **one row per day**. It shares `INSIGHTS_FIELDS` with the other two windows (`metaGraph.ts:362`, `:376`, `:393`), so every daily row already carries `actions` and `date_start` / `date_stop`. `countConversionActions` (`functions/src/metaSync/shared.ts:355-370`) already takes an **array of rows** and would yield a single day's count unmodified. Today these rows are consumed only by `spend7d` (`shared.ts:284`), `peak1dCtr` (`:307`) and `computeAgeDays` (`:1253`) — **the per-day `actions` arrays arrive on every sync and are never read.**
  - *The three-day window is NOT a per-day series and MUST NOT be used for this.* `fetchAdInsights3d` (`metaGraph.ts:353-366`) sends **no** `time_increment`, so Meta collapses the range into a **single aggregated row** — stated in the code itself at `shared.ts:294`. The `.reduce()` calls at `shared.ts:220` and `:266` iterate a one-element array and read as a per-day series without being one. This is recorded explicitly so the misreading is not repeated.
- **FR-082**: The accumulated total MUST be named **"conversions across days observed"** and MUST NOT be described, in code, comments, logs, or documentation, as a **lifetime** or **since-inception** total. It is not one.
  - *Three ways it can undercount, all in the same direction*: (1) a **per-ad insights fetch failure** — the fetch is per ad and a rejection is collected and skipped (`shared.ts:607-620`), so one ad can miss days while the account is otherwise fine; (2) **late attribution** — Meta may revise a day upward after the fact, and a day never revisited loses the revision; (3) **an ad ceasing to be returned** stops accruing days, the same absence problem the edge-case list already forbids treating as evidence. **All three undercount.** The total only ever grows, which is the property FR-077 needs, but it is not a lifetime figure and must not be called one.
  - **A fourth known inaccuracy runs the OTHER way, and this sentence must not be read as denying it.** FR-083's upward-only rule means a day that Meta later revises **downward** keeps its higher recorded value: **an over-counted day stays over-counted permanently.** That is the accepted cost of keeping FR-020's never-decreases guarantee unconditional, recorded in FR-083. So: three routes undercount, one route overcounts, and the total is **monotonically non-decreasing by construction** — which is the property FR-077 and FR-020 actually need, and is a different and weaker claim than accuracy.
- **FR-083**: A day's conversion figure MUST remain **revisable while that day is still inside the observed window**, and MUST be **finalised only once it falls out of the window**. Revision is **UPWARD-ONLY**: re-observing a still-open day **MAY raise** its recorded value and **MUST NOT lower** it. A re-observation reporting a **lower** figure is a **no-op**, not an overwrite. Re-observing a **finalised** day is the no-op FR-017 and FR-018 already describe, in both directions.
  - **Why upward-only rather than a plain overwrite (owner decision).** A plain overwrite breaches **FR-020**: if Meta revises a day's conversions downward — deduplication, fraud filtering, or a correction — the overwrite **decreases** an accumulated total, and FR-020 forbids any sync from decreasing a stored count, average or total. The accrual's overwrite is the **only** rule in this feature that can move a value in either direction, so it is the only place FR-020 could be breached from the inside.
    - *What the decision buys*: FR-020's never-decreases guarantee stays **unconditional**. That is the property the whole feature exists to provide — the owner's original requirement was that learning must not reset — and an unconditional guarantee is easier to trust and to test than one carrying an exception. It also makes FR-082's monotonicity claim **secured rather than asserted**, and leaves SC-001, SC-003 and SC-013 needing no qualification.
    - *The accepted cost, stated plainly*: **a day that was over-counted stays over-counted permanently.** Downward revisions from Meta are believed rare; a broken monotonicity guarantee would be permanent. The trade is deliberate.
  - *This is the fourth known inaccuracy, and the only one in the over-count direction* — see FR-082, whose "none can overcount" sentence is corrected there because this rule makes it false.
  - **POST-IMPLEMENTATION VERIFICATION (required, and recorded here because it cannot be done yet).** The accepted cost of upward-only is currently **visible but unmeasured**: nothing in the system stores a day's figure twice, so no evidence exists of whether Meta revises conversion counts downward, or by how much. This feature is the first thing to store per-day figures, which makes the question answerable **only after implementation**.
    - *The check*: once per-day figures are being stored, compare a day's recorded value across successive syncs **while that day remains inside the observed window**, and report whether downward revisions occur and at what magnitude.
    - *What it establishes*: it quantifies the cost this rule accepts. A negligible rate confirms the decision cheaply. **A material downward-revision rate is grounds to revisit the decision — deliberately, with the FR-020 trade re-argued — and never to reverse it silently**, because reversing it would reintroduce the FR-020 breach the rule exists to prevent.
    - *Why it is written into the specification rather than left in a report*: it is exactly the kind of item that is forgotten because it cannot be done at the time it is decided.
  - *Why this rule exists, and what it removes a dependency on*: the claim that the seven-day preset excludes today's partial day is **the repository's own assertion**, stated twice (`shared.ts:183-186`, `:281-283`) and **never verified against Meta**. It is load-bearing: if it is false, the current day is captured **partial**, and a no-op-on-first-sight rule would freeze it at its partial value **permanently** — not an occasional undercount but a systematic one, every day, on every creative. Making a day revisable until it leaves the window **removes the dependency on that assertion entirely**, because a partial day is corrected on the next sync that still sees it.
  - *It also absorbs the late-attribution caveat*: revisions arriving while the day is still in the window are captured rather than lost. Only revisions arriving after the day leaves the window are missed, which is a strictly smaller exposure than FR-082(2) describes without this rule.
  - *The unverified assertion is still recorded* (FR-082, and the Assumptions), but **the design no longer depends on it**.
- **FR-084**: The deduplication key for conversion accrual MUST be **(ad row id, date)**. A creative's total is the **sum across its rows** of its rows' per-day figures.
  - *Why nothing coarser works*: a creative spans up to **55** ad rows, each with its own per-day figures. Keying on (creative, date) would collapse 55 placements' conversions for one day into a single value and **drop 54 rows of evidence**; keying on ad row id alone would re-add every day the row is seen and **double-count**. Only the pair is both complete and idempotent.
- **FR-084a**: **Per-day entries MUST be retained only for days still inside the observed window.** When a day leaves the window it is finalised (FR-083) and its individual entry MUST be discarded, its value folded into a **running finalised total** and a **count of finalised days** held per ad row. Retention MUST NOT grow with account age.
  - **This is MANDATED by requirements already in the spec, not a storage optimisation.** FR-071 requires by-ID reads to return **whole documents, not projections**, and SC-023 requires the volume of prior-state data read per sync to be a function of the **current batch size only** and **not to grow with account age**. Ad documents may never be pruned (FR-066). Unbounded per-day entries therefore breach SC-023 *through* FR-071: every sync would read every day ever recorded for every ad in the batch. At the account sizes already measured — 1008 ad rows — indefinite retention is on the order of **367,920 entries per year**.
  - *Nothing is lost by collapsing*: FR-083 makes a finalised day **immutable**, and whether a day has left the window is **pure date arithmetic** against that sync's own window. **No stored flag is needed** to determine it, so a discarded entry cannot be needed again.
  - *Why the COUNT is retained and not only the total*: it lets the total be sanity-checked against the number of days that should have been observed, and it is the input FR-086's gap count needs. A total alone cannot distinguish a low figure from a short history.
  - *Accepted cost, recorded against FR-051a*: once collapsed, the ledger can no longer answer *"which days composed this total"*. This is consistent with FR-051a, whose audit guarantee is over **contributions to aggregates**, not over day-level accrual — but the distinction is stated here rather than left for a reader to reconcile.
- **FR-085**: Condition (b)'s stopped signal MUST be derived from the ad's **status**, which is **already requested and already discarded**. No new Graph API call is required.
  - *Evidence*: `HIERARCHY_AD_FIELDS` (`functions/src/metaGraph.ts:83`) requests `status`, and `MetaAd.status` is typed (`metaGraph.ts:145`) — but `ad.status` is never read in `shared.ts`, and `AdDoc` (`shared.ts:170-211`) has **no status member**, so the value Meta returns never reaches Firestore. Making it usable is a **write-site** change: persist a field already in flight.
  - *The real limitation — it UNDER-detects, it does not MIS-detect.* `status` carries the ad's **own configured** state, not parent-level pauses. An ad paused because its ad set or campaign was paused still reads as its own configured status, so such a stop is **not detected**. An undetected stop means the creative simply never seals via condition (b) — it waits for condition (a) or contributes no efficiency figure at all. **That is conservative and acceptable**; the failure mode is a missing contribution, never a wrong one.
  - *How the gap would be closed*: `effective_status` is a field on the **same** Graph call and distinguishes ad-level from parent-level pauses. Adding it is one field in `HIERARCHY_AD_FIELDS` plus one member on `AdDoc`. **Not required by this feature**, recorded so the option is visible rather than rediscovered.
- **FR-085a**: **A daily row absent from the insights response means the ad did not deliver that day. It MUST be recorded as NOT OBSERVED, never as zero conversions.**
  - *Why*: writing zero is drawing evidence from absence, which the edge-case list already forbids for an ad (*"Absence is not evidence of failure and must never reduce a count"*) and which applies identically to a day within a returned ad's window. Under FR-083's upward-only rule the two readings converge for a day that already has a value — zero cannot lower it — but they **diverge on a day's first observation**, and they diverge on whether a never-delivered day is *finalised at zero* or *never observed at all*.
- **FR-086**: Conversion accrual depends on the **daily dispatcher** (`functions/src/metaSync/dispatcher.ts:137`, `"0 3 * * *"`). A sync observes days D−7 … D−1, so **up to six consecutive missed syncs are absorbed with no gap**; from the **seventh**, days are lost **permanently and silently**, because no call the sync makes offers them again.
  - The per-sync summary line MUST report a **count of days lost to gaps**, alongside the link-provenance breakdown of FR-076. Without it the seventh missed sync is indistinguishable from the sixth.
  - **FR-086a**: **The days-lost count MUST track dates that NO sync's window covered — not dates for which Meta returned no row.** The two are different and conflating them destroys the count's value as an alarm:
    - A date **inside** an observed window with **no row returned** → the ad did not run that day (FR-085a). **This is NOT a gap and MUST NOT increment the count.**
    - A date that fell **outside every observed window** because syncs were missed → genuinely unrecoverable. **This IS a gap and MUST increment the count.**
    - *Why the distinction is load-bearing*: a paused or low-budget ad produces absent rows constantly. If those incremented the count, it would read non-zero continuously and an operator would learn to ignore it — so a real seven-day outage, the thing SC-042 requires it to catch, would arrive as noise inside noise. The count must be **zero in normal operation** to function as an alarm at all.
    - *The test is clean*: whether a given sync's window covered a date is **pure date arithmetic** from that sync's own window bounds, requiring no stored state and no inference from Meta's response.

- **FR-087**: **THE RECOMPUTATION RULE. The efficiency figure is RECOMPUTED when the creative's set of rows changes. It is CARRIED ACROSS UNCHANGED when only its destination changes.**
  - *Rationale*: the figure is a function of the creative's rows and its sealed target (FR-002a, FR-012a). **If those inputs are unchanged, the output must be unchanged** — recomputing would breach FR-079. **If the row set genuinely changed, the previous figure was computed over an incomplete set**, and carrying it forward would preserve an error.
  - This rule is the single governing statement for both cases below, and is referenced from FR-013, FR-074b, FR-079 and FR-080 rather than restated in each.
  - **(i) Re-attribution (FR-011(b) / FR-013) — CARRY ACROSS.** The creative keeps every row; only the angle and visual pattern it lands in change. Same rows, same sealed target, same inputs, therefore the same number.
    - *Why FR-079 and FR-080 do not conflict*: FR-080's withdraw-then-add moves **where** the figure is counted; FR-079 governs **what the number is**. Once that distinction is stated they are orthogonal. SC-035 (the figure is retained) and SC-036 (one withdrawal, one addition) therefore both hold, and neither depends on the other's reading.
  - **(ii) Merge (FR-074b) — RECOMPUTE over the union.** A merge changes the row set, so this rule requires recomputation. The two pre-merge figures were each computed over **half the evidence**, because the split was a **mis-identification, not a real division**.
    - *A merge is an IDENTITY CORRECTION and belongs under FR-080's attribution exception, not under FR-079's prohibition.* Stated explicitly because the natural reading of FR-079 forbids it.
    - *When both halves have already contributed a figure*: **withdraw both, recompute over the union against the surviving sealed target, add one** (FR-013, extended for this shape).

### C. Cumulative, Idempotent Accumulation

- **FR-015**: Angle and visual-pattern records MUST accumulate across the entire history of the account. A stored record MUST represent all-time evidence, not the most recent sync's evidence.
- **FR-016**: The system MUST maintain, for every **ad row**, a durable record of exactly what that row has already contributed to the learning aggregates — the angle, the visual pattern, the bucket, and every measured value folded in.
  - *Unit versus storage (FR-073)*: the ledger stays **per ad row**, because the ad document is what the sync reads by ID and what makes idempotency checkable. The **evidence** those entries add up to is per **creative** (FR-074). A creative's contribution to an angle record is the roll-up of its rows' ledger entries, counted once for the creative — not once per row.
- **FR-017**: On each sync, for each eligible ad, the system MUST compare the contribution the ad *should* make against the contribution it has *already made*, and act as follows:
  - No prior contribution → **add**.
  - Prior contribution identical to the desired one → **no-op**. Nothing is written and no count moves. This is the idempotency guarantee.
  - Prior contribution differs (material change per FR-011) → **withdraw the prior contribution, then add the new one**.
- **FR-018**: Processing the same sync payload any number of times MUST leave the stored learning records in exactly the state produced by processing it once. No ad may ever be counted twice.
- **FR-019**: The system MUST NOT write to an angle's or pattern's record when that angle or pattern received no change in this sync. An untouched record is left untouched.
- **FR-020**: A sync covering a subset of the account's ads MUST NOT decrease any stored count, average, or total. Absence of an ad from a sync is not evidence and carries no weight.
- **FR-021**: Records MUST store the raw sums and counts from which averages are derived, so that a contribution can be added or withdrawn exactly, without recomputing from history and without accumulating rounding drift across repeated operations.
- **FR-022**: Records MUST also carry the derived averages under their existing names and units, so existing readers continue to work without change.
- **FR-023**: Accumulation MUST be safe under concurrent syncs for the same account: two writers touching the same record must not lose or duplicate a contribution. The mechanism is specified in section J.

### D. Preserved Measures

- **FR-024**: Click-through and cost-per-thousand measures MUST retain their current names, units, meaning, and funnel-blindness. The only change permitted is that their accumulation window widens from "the last sync" to "all time" — which is the correction this feature exists to make, not a restructuring of the measure.
- **FR-025**: The existing partitions — objective bucket, geographic tier, and audience type — MUST be preserved unchanged in name and meaning.
- **FR-026**: The verdict engine MUST NOT be modified. All changes occur at the write site and the read sites.

### E. Funnel Type: Weighting, Never Exclusion

- **FR-027**: Angle and visual-pattern records MUST carry a per-funnel-type breakdown of their evidence, including an explicit bucket for unknown.
- **FR-028**: Funnel type MUST NOT be part of a record's identity. One angle has exactly one record spanning every funnel type the owner has ever run.
- **FR-029**: A record's headline totals MUST remain the all-funnel totals, so any reader that ignores the funnel-type breakdown sees the complete cross-funnel evidence.
- **FR-030**: Retrieval MUST use funnel type only to **weight** results toward same-funnel evidence. It MUST NOT use funnel type to filter, exclude, suppress, or zero any angle or pattern.
- **FR-031**: An angle with strong evidence and zero same-funnel evidence MUST remain eligible for recommendation and MUST remain capable of ranking among the top recommendations.
- **FR-032**: Evidence recorded under the **unknown** funnel bucket MUST receive no same-funnel weighting boost for any requested funnel type, and MUST NOT be treated as matching the requested type. It MUST still count toward the record's headline totals and MUST NOT be excluded from retrieval — unknown provenance is weaker evidence, never disqualifying evidence. This is the only reading consistent with FR-030 and FR-031.
- **FR-032a**: The efficiency figure MUST be usable as a cross-funnel comparison basis: because it is target-normalised, evidence gathered under one funnel's economics is directly comparable to evidence gathered under another's.

### F. Reading Surfaces

- **FR-033**: The creative-guidance retrieval path MUST read the new record shape. The change is additive: existing selection behaviour based on click-through against the account average is retained.
- **FR-034**: The sample-size threshold that activates learned guidance MUST be retained at **10**, and MUST now be counted in **distinct creatives** (FR-073), not ad rows. Its meaning changes, and the change MUST be recorded as a **provisional** decision pending real usage data — not asserted as still-correct.

  **What 10 used to represent.** Under the replaced semantics, the threshold counted matched, result-driving ads present in a *single* sync. Because a sync reflects the account's currently-returned ads, meeting it required roughly ten such ads to exist *concurrently*. That is a substantial bar: it implied an account of real size, actively running, right now.

  **What 10 represents under this feature.** Ten **distinct creatives across all time** (FR-073), in any combination of funnels, in any combination of time periods. A creative running in twenty ad sets still counts once.

  **What counting creatives rather than rows costs, stated deliberately.** At the observed **7.4:1** fan-out on `act_995888422231015`, each of the three gates (FR-034, FR-034a, FR-037) becomes roughly **seven times harder to reach** than under row counting. Activation at 10 creatives corresponds to roughly **74 ad rows** of activity. **This delay is accepted deliberately.**

  **What it buys, and why row counting was not merely slower but wrong.** Under row counting, the single 55-row creative in `act_995888422231015` cleared all three gates **by itself** — 55 rows past a 10-row activation threshold, a 3-row per-item floor and a 3-row efficiency gate. That is precisely the thin-evidence failure FR-034a was added in Iteration 3 to prevent: one observation driving a top recommendation. Row counting meant that floor never actually closed the hole it was written for. Counting creatives closes it.

  **Two properties are genuinely lost, and neither is recovered by this feature** (both predate Amendment 1 and are unaffected by it)**:**
  1. **The concurrency bar is gone.** Ten ads that never ran at the same time now clear a gate that previously required ten running together.
  2. **An implicit recency property is gone.** The old per-sync window incidentally guaranteed the evidence was *current*. All-time counting removes that guarantee entirely. Ten ads accumulated over six months may reflect creative approaches, audiences, and market conditions that no longer hold, and nothing in the threshold detects this.

  **Why the value is not being changed now.** Raising it would be a guess. There is no usage data to calibrate against, there is one user, and a higher bar delays the feature's value for that user with no evidence that it buys better signal. Lowering it is plainly unsafe. Ten is retained as the incumbent value, carried forward deliberately rather than by default.

  **This is therefore marked PROVISIONAL.** It MUST be revisited once the first account has accumulated real cumulative evidence. **The review trigger is restated for the changed unit (Amendment 1):** the value 10 was calibrated against ad rows and is now applied to creatives, which at the observed 7.4:1 fan-out makes it a materially higher bar than any figure this project has ever run against. Whether 10 creatives is too many, too few, or right is now **entirely uncalibrated** — carrying the number forward preserves the constant, not its evidential meaning. The review MUST examine: whether guidance activated before the evidence was worth acting on; whether it failed to activate at all for an account doing real work, which row counting would have activated; whether the evidence at activation was concentrated in a single funnel type or a single stale time period; and whether accounts that activated early produced worse creative than accounts that activated later. Any of those findings justifies raising the threshold, adding a recency qualifier, or splitting the single threshold into separate account-level and per-funnel gates. **No structural change is required to act on that finding** — the threshold is a named constant.

  **A known reason the count may run high, which the review MUST weigh (FR-074b).** The cross-group merge that keeps one creative from being counted twice requires a generation link, and most rows have none — on `act_995888422231015`, none at all. Two unlinked hash groups that are one creative therefore stay two creatives, **inflating** the distinct-creative count and making this threshold fire **earlier** than the seven-times-harder bar argued for above. So if the review finds guidance activated on thinner evidence than expected, split creatives are the first thing to check, and the correct remedy may be improving link coverage rather than raising the number.

  **Correction to the prior draft.** An earlier version of this requirement justified the value partly by claiming the downstream ranking rules retain their own independent minimum-evidence gates. That is true of the "avoid" list, which requires at least 3 ads per angle, but it is **not** true of the top-performer list, which today admits any angle with at least one qualifying ad. Weakening the account-level gate without noticing that gap would allow a single-ad angle to become the top recommendation. FR-034a closes it.

- **FR-034a**: An angle or visual pattern MUST NOT appear among the recommended top performers until it carries at least **3** contributing **creatives** (FR-073) of its own. This per-item floor is required because the account-level threshold in FR-034 is materially weaker than the one it replaces; the account gate alone no longer guarantees that any individual recommendation rests on more than one observation. The value matches the existing minimum used by the "avoid" list, so both directions of the recommendation now rest on the same evidentiary floor.
- **FR-035**: Once the activation threshold has been met for an account, a subsequent partial or failed sync MUST NOT switch learned guidance back off.
- **FR-036**: The sample size used for the activation decision MUST count **distinct creatives** (FR-073). Neither repeated observation across syncs nor multiplicity of ad rows may inflate the count: a creative running in twenty ad sets counts once, and a creative seen in twenty syncs counts once.
- **FR-036a**: PROVISIONAL contributions MUST count toward the activation threshold and toward the per-item floor in FR-034a. A creative is PROVISIONAL for this purpose when it carries no sealed target; the state is a property of the creative, not of an individual row — derived from its rows by FR-036c.
  - *Justification*: a threshold should count the ads that carry the measure it gates. Everything the activation threshold controls — the recommended angles, the avoid list, the caption guidance — is driven by click-through, and click-through is target-independent, which is exactly the property that makes it accumulate across funnels in the first place. A PROVISIONAL creative carries complete, valid click-through evidence; only its efficiency figure is missing. Excluding it would withhold guidance from an owner with real evidence purely because a settings document was incomplete, which converts a setup problem into an evidence problem. The efficiency figure retains its own independent gate under FR-037, counted only over creatives carrying a sealed figure. Two measures, two gates, each counting the creatives that actually carry it.
- **FR-036c**: **A creative's contribution state MUST be derived from its rows as follows: the creative is SEALED if *any* of its rows is SEALED, and PROVISIONAL only while *every* row is PROVISIONAL.** When the creative is SEALED, its sealed context is the one belonging to the first row to seal (FR-012a), and rows that seal later or join later inherit it.
  - *Why any-row rather than all-rows*: the state machine is one-way (FR-005c). Once any row has sealed, a resolvable target has been recorded for that creative and cannot be un-recorded, so "PROVISIONAL" would be a false statement about the creative from that moment on. Requiring all rows would also mean a single new placement appearing during a settings gap could drag an already-sealed creative back toward PROVISIONAL — precisely the reverse transition FR-005c forbids.
  - *Why mixed states are rare, stated rather than assumed impossible*: sealing turns on whether the **account's** funnel economics are resolvable (FR-005d), not on anything the row carries. All rows of a creative present at the same evaluation therefore seal together. A mixed state arises only in one shape — a row that **first appears during the settings gap**, after some of its siblings have already sealed. That is uncommon but reachable, so the rule is stated rather than left to the fact that it usually will not happen.
- **FR-036b**: When a PROVISIONAL contribution seals, it MUST NOT increment the distinct-**creative** count again. The creative was already counted; sealing changes what it carries, not whether it exists. Equally, a creative gaining an additional ad row MUST NOT increment the count — the row is a new placement of evidence already counted.
- **FR-037**: The efficiency figure MUST NOT influence ranking for an angle or pattern until that angle or pattern has at least **3** **creatives** (FR-073) carrying a sealed efficiency figure, consistent with the existing minimum-evidence gate used elsewhere in retrieval.
  - **Stacked-gate consequence, stated rather than discovered (Amendment 2).** FR-077 requires **5 conversions per creative** before that creative contributes an efficiency figure, and this requirement needs **3 such creatives** before efficiency influences ranking. The two compose: **an angle needs 15 conversions, spread across at least 3 distinct creatives, before efficiency affects its rank at all.** Neither value is changed — this is a recorded consequence, not a proposal — but it must be visible, because 5 and 3 each look modest in isolation and their product does not. On a Gulf coaching account this is the difference between efficiency mattering in weeks and mattering in months, and it compounds with FR-034's creative-counting change in the same direction: both make guidance later and better-evidenced.
    - *And it can be pushed further out by a cause outside these numbers*: a **split creative** (FR-074b's limitation) splits its conversions too, so a creative divided in two may reach neither half's threshold where the whole would have cleared it comfortably. See the split-conversion note under FR-077's section.
  - *Open dependency now closed by Stage 1B — "carrying a sealed efficiency figure" is defined at creative scope by FR-077 and FR-002a.* FR-036c derives a creative's **state** (SEALED / PROVISIONAL) from its rows, but state and figure are **not the same thing**: FR-006 seals a contribution whose efficiency figure is explicitly **absent**, so a creative can be SEALED and carry no figure. This gate counts creatives carrying a **figure**, not creatives in the SEALED state, and the rule that decides when a creative has one is Amendment 2's eligibility rule. Flagged here so the two are not conflated in the meantime.
- **FR-038**: The value folded into an angle's or pattern's average efficiency MUST be bounded at **3.0**, while the raw unbounded figure is retained on the ad's own record.
  - *Justification*: the verdict engine already treats 2.5× target as its worst-case ceiling; beyond 3× an ad is unambiguously a loser and further magnitude carries no additional decision value, only leverage over the average. Bounding at the aggregate rather than at the source keeps the ad-level record honest and auditable.
- **FR-039**: The "What's Working" dashboard MUST read the new record shape. Its existing tier icons, which are derived from click-through against the account average, MUST continue to work.
- **FR-040**: The counts the dashboard presents MUST be the all-time totals.
- **FR-041**: The dashboard MUST show a plain-language indication when an angle's or pattern's evidence spans more than one of the owner's funnels.

### G. Retirement of Prior Records (no migration)

- **FR-042**: Learning records MUST carry a schema version.
- **FR-043**: Readers MUST treat any learning record below the current schema version as **absent** — contributing zero, not partially counted, not mixed with new evidence.
- **FR-044**: The first write to a record below the current schema version MUST **replace the record in full**, so that no stale field from the retired shape can survive alongside the new one. It MUST NOT be an increment onto the old record.
- **FR-045**: No prior count, average, or total may be carried forward into the new shape. Learning starts clean.
- **FR-046**: An ad performance record with no recorded contribution is treated as never having contributed, and its row will make its first contribution on the next sync that includes it. Absence of a ledger entry is a statement about that **row**, never about the creative: a creative whose other rows have already contributed is already represented, and a newly-appearing row of it adds a placement, not a second creative (FR-036b).

### J. Serialized Learning Writes

- **FR-054**: Learning accumulation for a single ad account MUST be serialized by a **lease**. Only one run may perform the ledger's read-compare-write and the resulting aggregate deltas for a given account at a time.
  - **FR-054a**: **The lease MUST be placed inside `runSyncForAccount`, around the learning write itself — NOT at the orchestrator level.** Every route to the learning write passes through `runSyncForAccount`; an orchestrator-level lease does not.
  - **FR-054b**: **Phase 970's existing lease MUST NOT be cited as satisfying this requirement, because it does not reach the fan-out path.** `runFullSyncWithLease` (`functions/src/metaSync/orchestrator.ts:824`) acquires at `:841` and wraps the whole of `runFullSync` at `:871-873`, and `runFullSync` has no other caller — so the **manual, inline** route is leased. But `metaSyncAccountWorker` imports `runSyncForAccount` directly (`functions/src/metaSync/worker.ts:19`) and calls it at `:61` with **no** `acquireLease` and **no** `runFullSyncWithLease`. The Cloud Tasks fan-out and the entire 03:00 scheduled cycle therefore reach the learning write **unleased**, and that is the route carrying most of the volume.
    - *Scope difference as well as placement*: Phase 970's lease is keyed **per owner** (`metaSyncLeases/{ownerUid}`, `functions/src/metaSync/lease.ts:52`, `:77`) with a **10-minute** TTL (`lease.ts:53`); this requirement's lease is **per account** with the TTL in FR-059. They are different documents answering different questions. **FR-059's Phase 970 clarification previously said the opposite** — that the two share the document `metaSyncLeases/{ownerUid}` and are merged into one artifact selecting a TTL by call site — and has been **corrected** to match this requirement. A per-owner key cannot serialise per account, so the merged design cannot express FR-054a at all.
  - **FR-054c**: **The concurrency this lease MUST defend against is concrete, not hypothetical: two or more `runSyncForAccount` invocations for the SAME ad account, in flight simultaneously, with no platform-level deduplication available.**
    - *No platform dedup exists.* Cloud Tasks deduplicates only against a **caller-supplied** deterministic task name. Neither enqueue site supplies one — both build a task object containing only `httpRequest` (`orchestrator.ts:588-611`, `dispatcher.ts:162-179`) — so Cloud Tasks generates names and two enqueues for one account produce two independent tasks.
    - *`maxConcurrentDispatches: 5` does not prevent it.* That cap (`worker.ts:39`) is **queue-wide**, not per-account; nothing constrains its five slots to five distinct accounts.
    - *Three independent routes to a same-account pair*: (1) the 03:00 dispatcher (`dispatcher.ts:137`) and a manual press's fan-out (`orchestrator.ts:698`) enqueue from separate code paths with no shared registry; (2) `maxAttempts: 3` with 30–600 s backoff (`worker.ts:33-37`) can retry a task while the original invocation is still running; (3) the dispatcher de-dups by `accountId` only **within a single run** (`dispatcher.ts:100-104`), not across runs and not against the manual fan-out.
    - *Why this matters more under Amendment 1 and 2 than it did before*: under today's overwrite semantics two concurrent workers write the same value twice and the result is the same value. Under delta-only accumulation (FR-021) they **add the same conversions twice**, silently, into the figures that steer generation. Cloud Tasks retries are the named reason this requirement exists.
  - **FR-054d**: **LEG A — the relocated legacy sync — is verified NOT to require lease coverage, and this is recorded so it is not re-litigated.** It runs **inside** Phase 970's lease and is `await`-sequenced **before** LEG B (`orchestrator.ts:652`), so it never runs concurrently with the learning block within one sync. It writes five paths — root `adPerformance` (`orchestrator.ts:404`), `adPerformanceHistory` (`:408`), `creativeDeployments` (`:453-457`), `metaConnections` (`:471-473`), and the workspace-private `metaConnection` (`:480-482`) — **none of which the learning path reads**: the two `adPerformance` references in `shared.ts` (`:831`, `:1025`) are the *workspace subcollection* under `adAccountRef` (`shared.ts:818-821`), a different collection from the root one LEG A writes, and `learningAggregates.ts` is pure (no Firestore access at all).
    - *The one shared field, and why it is not the cooldown class*: both legs write `lastMetaSyncAt` on the same workspace-private document (LEG A at `orchestrator.ts:480-482`; LEG B via `patchStoredConnection` → `privateConnectionRef`, `functions/src/metaConnection.ts:44-49`). **Nothing reads it as a gate.** `shared.ts` never reads it; the only readers are two display surfaces; the 1-hour cooldown that did read it was removed by Phase 970 Batch 4; and `lease.ts:31-35` deliberately keeps the lease on a **separate document** so it cannot alias into a cooldown-side read or write. The last-writer-wins race between the two legs moves a displayed timestamp by milliseconds and nothing else.
- **FR-055**: The lease MUST cover **only the learning write** — the ledger comparison, the contribution decisions, and the aggregate delta writes. It MUST NOT cover the whole sync.
  - *Rationale*: two runs fetching Meta data, computing metrics, and writing operational status concurrently is harmless — those writes are idempotent overwrites of per-ad facts. Only the check-then-act on the ledger is racy. Scoping the lease to the learning write keeps the held window to a small fraction of a sync, which proportionally shrinks every failure mode the lease itself introduces.
- **FR-056**: Acquisition MUST be **atomic**. The primitive is a **database transaction over a single lease document**, which reads the current lease and writes a new one only if the document is absent or its expiry has passed. Transactional isolation on the read document is what makes two simultaneous acquisitions mutually exclusive; a plain read followed by a write reintroduces the exact race the lease exists to eliminate and MUST NOT be used.
- **FR-057**: The lease MUST carry a unique **holder identity** for the run that acquired it, and an absolute **expiry timestamp**.
- **FR-058**: Release MUST also be atomic and MUST verify holder identity — a run may only release a lease it still holds. A run whose lease already expired and was taken over MUST NOT be able to release its successor's lease.
- **FR-059**: The lease MUST **expire on its own** with a time-to-live of **15 minutes**.
  - *Justification*: both sync entry points are capped by the platform at 540 seconds (9 minutes), after which the runtime terminates the process — no sync can exceed this, so 15 minutes sits roughly 6 minutes above a ceiling that cannot be crossed. That headroom absorbs clock skew and leaves room for a process killed mid-run to hold a stale lease briefly without ever blocking a legitimate successor for a meaningful period. The scheduled cycle is 24 hours, so a worst-case stranded lease self-clears long before the next **scheduled** attempt. **CORRECTED (Amendment 1 review): the second half of this argument — that “the manual path carries a 1-hour cooldown” — is FALSE as of Phase 970.** Batch 4 removed the cooldown and replaced it with an in-flight guard (`functions/src/metaSync/trigger.ts:8`, `:54`; `functions/src/metaSync/orchestrator.ts:476`, `:651`). Nothing now rate-limits a second manual press except that guard, so a stranded lease **can** be met by a legitimate manual attempt inside the TTL. The TTL is retained at 15 minutes on the strength of the platform-ceiling argument alone, which does not depend on the cooldown; the manual-path argument is struck rather than left to prop it up. A lease with no expiry is forbidden outright: a crash or platform timeout would lock that account's learning permanently, recoverable only by manual intervention.
  - **Recorded inconsistency — the surviving argument is calibrated against the wrong window. The value is NOT changed here.** The 540-second ceiling bounds a **whole sync**, but FR-055 scopes this lease to *"only the learning write ... a small fraction of a sync"*. The lease is therefore held for a fraction of the window its headroom is measured against, which makes **15 minutes considerably larger relative to what it actually guards** than the ceiling argument implies. The number is retained because no better-calibrated figure is available without production timing data on the learning write itself, and an over-long TTL fails safe (it delays a legitimate successor) rather than unsafe (it would permit two writers). Planning MAY revisit it once the held window is measurable.
  - **Second-order inconsistency, with the cooldown gone.** FR-059 now states that a stranded lease can be met by a legitimate manual press inside the TTL. FR-065's owner-facing message says *"try again in a few minutes."* Against a **15-minute** worst case that message is optimistic. **The strings are NOT rewritten in this stage** — the English and Arabic in FR-065 are unchanged — but the inconsistency is recorded so it is resolved deliberately rather than discovered by an owner who waited three minutes and was refused again.
  - **Phase 970 clarification — CORRECTED. The two leases are DIFFERENT DOCUMENTS WITH DIFFERENT KEYS, and MUST NOT be one artifact.**
    - **The in-flight sync guard** (`functions/src/metaSync/lease.ts`) is keyed **per owner** — `metaSyncLeases/{ownerUid}` (`lease.ts:52`, `:77`, `:115`, `:172`) — with a **10-minute** TTL (`lease.ts:53`). Its job is to suppress concurrent presses by one owner, not to make a crashed press visible days later, which is why its TTL sits below the platform ceiling.
    - **The learning-write lease** required by FR-054 is keyed **per ad account** and MUST live in its **own collection, distinct from `metaSyncLeases`**. The document key MUST be the (owner, ad account) pair; the collection name itself is a planning choice, but **the key is a contract** and a per-owner key does not satisfy it.
    - **Why a single artifact selecting a TTL by call site is now forbidden**: a lease keyed on `ownerUid` **cannot serialise per account**. An owner with three ad accounts would have all three contending for one document, so the learning write for account A would block account B for no reason; and a manual press holding the guard would block the learning write for **every** account that owner has. FR-054a requires the lease inside `runSyncForAccount`, which runs per account, so the merged artifact is not merely undesirable — it cannot express the requirement. The previous version of this clarification described that merged design; it is **struck**, not softened.
    - *Sharing the record SHAPE remains fine* — holder identity plus absolute expiry (FR-057) — and both still satisfy FR-056's atomicity primitive independently. What may not be shared is the **document** or the **key**.
- **FR-060**: A run that cannot acquire the lease MUST behave differently depending on how it was triggered:
  - **Manual** — fail fast and tell the owner, in their language, that a refresh is already running and to try again shortly. The owner is present and can retry; a hanging call is worse than a clear answer.
  - **Scheduled** — MUST NOT fail silently and MUST NOT skip. It MUST signal failure in the way the existing task infrastructure already understands, so the run is retried with backoff rather than dropped. The existing retry configuration (3 attempts, 30s to 600s backoff) is sufficient and needs no change.
- **FR-060a**: **ORDERING IS MANDATORY, and it resolves FR-052 against FR-060 without a trade-off.** Now that FR-054a places the lease **inside** `runSyncForAccount`, the sequence within a run MUST be:
  1. Fetch, compute, and **COMMIT** the operational status writes FR-009 requires.
  2. **Then** attempt to acquire the learning-write lease.
  3. If acquisition fails, signal failure in the form the task infrastructure acts on (FR-060) — **after step 1 has already committed.**
  - **Why no trade-off exists.** The apparent conflict assumes that failing the invocation discards the writes made before it. **It does not**: signalling failure to the task infrastructure does not roll back a committed database write. Writes already committed remain committed, the run is retried, the operational writes re-apply harmlessly — FR-055's own rationale establishes that they are *"idempotent overwrites of per-ad facts"* — and the learning write gets another attempt. **Nothing is discarded, and FR-052's guarantee is intact, because the learning failure did not break the sync's operational work.**
  - **Why this is stated explicitly rather than left to the implementer.** The wrong ordering — attempting the lease **before** committing operational writes, or throwing without committing at all — is the natural thing to write, and nothing in FR-052, FR-054a or FR-060 as previously worded forbids it. Getting it wrong means a contended account's ads silently stop having a current operational status (FR-009) while every retry re-fetches the whole account to reach a learning write that may still be contended.
  - *This applies to the manual path too*: the fail-fast message of FR-060 and FR-065 is emitted **after** the operational writes have committed, so an owner who is told a refresh is already running still gets a current action list from the run that told them.
- **FR-061**: If a scheduled run exhausts its retries because the lease was held throughout, that is **not** a loss of learning and MUST NOT be treated as one. Contention means another run was writing that account's learning at the time. The dropped run is deduplication, not data loss. The one case worth noting is a full scheduled run losing to a narrower manual one; FR-020 guarantees the narrower run cannot shrink anything, and the next scheduled cycle restores full coverage.
- **FR-062**: A run MUST re-verify that it still holds the lease — matching holder identity and unexpired — **immediately before committing** its learning writes, and MUST abort the learning write entirely if it does not. A run whose lease was force-expired and taken over MUST NOT continue writing alongside its replacement.
- **FR-063**: The residual window between that final check and the commit MUST be acknowledged rather than papered over: the check narrows the window, it does not eliminate it, because the commit itself cannot be made conditional on the lease. This is accepted because FR-059's time-to-live exceeds the platform's own execution ceiling, which makes takeover-while-running unreachable under normal operation; the check exists for the pathological case, not the expected one.
- **FR-064**: Aborting a learning write under FR-062 MUST leave existing records untouched and MUST NOT fail the surrounding sync, consistent with FR-052. The abort MUST be recorded as an auditable event.
- **FR-065**: The "already refreshing" message MUST ship in English and simple Fusha Arabic, free of technical terms, per FR-047 and FR-048:
  - English: "Your ad data is already being refreshed. Please try again in a few minutes."
  - Arabic: "يتم الآن تحديث بيانات إعلاناتك. حاول مرة أخرى بعد بضع دقائق."

### K. Ledger Durability and Bounded Reads

- **FR-066**: Ad performance documents MUST NOT be pruned, aged out, or deleted by any retention policy. The reason MUST be stated in the document itself, at the collection's write site, so that anyone later adding a retention policy encounters it before writing the code rather than after: **the contribution ledger lives on the ad document and is authoritative for correctness — deleting an ad document silently re-enables double-counting**, because the ad then reads as never having contributed and is added again the next time it appears.
- **FR-067**: The ledger and the other prior-state fields MUST be read **by document ID, for exactly the ads in the current batch**, never by scanning the collection. Correctness MUST NOT depend on an unbounded scan completing.
- **FR-068**: The existing unbounded collection read MUST be **removed entirely**, not left in place beside the new one. Two paths reading the same data is how the removed one survives a refactor and quietly becomes authoritative again.
- **FR-069**: By-ID reads MUST be chunked, and **every chunk MUST complete before any write is issued**, so a partially-read ledger can never produce a partially-applied contribution decision.
  - *Cap and chunk size*: a value-list query (`in` on document ID) is capped at **30** values per query, which is too small to be practical here. A direct multi-document fetch has **no documented per-call document-count cap** — it is bounded by request and response size and by the call deadline — so the chunk size is a policy choice rather than an API limit. It MUST be set to **300**, which is conservative against response size, clears any realistic per-sync ad count in a small number of chunks, and is consistent in spirit with the write path's existing 450-operation chunking.
- **FR-070**: A failed chunk read — timeout, quota exhaustion, or any transient error — MUST NOT be treated as "these ads have no prior contribution". It MUST **abort the learning write for that chunk**, leaving those ads' existing contributions untouched.
  - *Rationale*: an empty result and a genuinely absent contribution are indistinguishable at the call site, and conflating them re-adds every ad in the chunk, producing precisely the double-count FR-018 forbids. A read failure is missing information, never evidence of absence. This MUST be covered by a test that forces a read failure and asserts no contribution was added.
- **FR-071**: By-ID reads MUST return **whole documents**, not projections. Fields written by the delete cascade (`deletedGenerationId` and the cascade's `metadataAvailable` mark) live outside the strict shape the sync writes, and a projection would silently break the cascade-preservation behaviour.
- **FR-072**: Three existing behaviours besides learning read this prior state and are therefore **explicitly in scope** for the read-pattern change. All three are per-ad lookups for ads already in the current batch, so the bounded read is behaviour-identical for each, and each MUST be verified as unchanged:
  - the match-link precedence lock, where a prior manual or automatic link locks the ad's attribution;
  - the delete-cascade preservation flag, which stops the sync from undoing a cascade mark;
  - the matched / ambiguous / unmatched tallies, which derive from the locked attribution values.
- **FR-072a**: **Amendment 1 introduces a third link provenance (FR-074e), and FR-072's "behaviour-identical" claim MUST be re-stated against it rather than assumed to survive.** Because FR-074f places provenance in a **separate field** and leaves `matchType` untouched, each of FR-072's three behaviours is affected as follows:
  - **The match-link precedence lock** (`shared.ts:864-869`) — **unaffected, and deliberately so.** It branches on `matchType`, which gains no new value. A propagated-only row keeps `matchType` `null`, so the lock does not fire and the row stays re-matchable, which is exactly what FR-074e requires. What MUST be verified is the negative: that a propagated link never causes the lock to fire.
  - **The delete-cascade preservation flag** — **unaffected.** It reads `metadataAvailable` and `deletedGenerationId`, neither of which provenance touches. What MUST be verified is that a propagated row is cascaded like any other row of its creative, consistent with FR-014's creative-scoped effect.
  - **The matched / ambiguous / unmatched tallies** — **unaffected in value, and their meaning is now stated explicitly.** See FR-072b.
- **FR-072b**: **A row carrying only a propagated link MUST be counted as `unmatched` in the existing matched / ambiguous / unmatched tallies.**
  - *Why not `matched`*: counting it as matched would restate FR-076's problem on a second surface — the tallies would report improving match coverage produced entirely by propagation, while direct matching degraded unseen. The tallies are, and MUST remain, a measure of **direct** match coverage.
  - *Why not a fourth tally bucket*: the tallies are a pre-existing surface FR-072 requires to be behaviour-identical, and a propagated-only row has `matchType` `null` (FR-074f), so it already falls to `unmatched` with **no code change and no value change**. Adding a bucket would break the identity FR-072 exists to protect. Propagated contributions are reported in **FR-076's provenance breakdown**, which is the surface built for that purpose.
  - *The apparent oddity is deliberate*: a propagated row **contributes to learning** while being **counted as unmatched** in the tallies. These answer different questions — "is this creative's evidence attributable?" and "did perceptual matching find this row?" — and conflating them is what FR-076's justification warns against. Both surfaces MUST be read together, and the spec says so rather than making them agree by weakening one.

### Key Entities

- **Ad Performance Record** — one per **ad row**. Already carries measured performance, creative attribution, and an operational status. Gains: the **sealed target**, the **sealed efficiency figure**, the **sealed funnel type**, the **sealed learning result**, and the **contribution ledger entry** describing exactly what this row has folded into the aggregates. It is the **storage location** of the ledger, not the unit of evidence (FR-073).
- **Creative** — the **unit of evidence** (FR-073). A group of ad rows sharing an `imageHash`, resolved to a single `generationId` where any row in the group carries one, with manual attribution winning any disagreement (FR-074, FR-074a); groups resolving to the same `generationId` are then **merged** (FR-074b), and a linked row with no hash joins its generation's creative directly (FR-074c). It is a **derived grouping, not a stored document**: it has no record of its own, and every gate that counts evidence — FR-034, FR-034a, FR-036, FR-037 — counts creatives.
- **Contribution Ledger Entry** — one per **ad row**, carried on that row's own record, not in a separate store, so it is loaded by the reads the sync already performs. Describes the angle, the visual pattern, the bucket, and every value contributed, plus the measurement inputs that produced it. This entry is the sole mechanism of idempotency: comparing desired against recorded is what makes a repeated sync a no-op. The entries of the rows belonging to one creative roll up to that creative's single contribution (FR-016).
- **Hook Angle Record** — one per canonical angle, spanning all funnel types. All-time sums, **counts of contributing creatives** (FR-073), derived averages, win and loss totals, efficiency totals, and a per-funnel-type breakdown. Identity is the angle alone; funnel type is a dimension inside it, never part of its identity. Every count in this record is a count of creatives, never of ad rows.
- **Visual Pattern Record** — one per visual pattern key, with the same structure, the same identity rule, and the same creative-counting rule.
- **Sealed Evaluation Context** — the tuple of target, efficiency figure, funnel type, and the moment of sealing. Fixed when the contribution transitions to SEALED and thereafter immune to settings changes. **Single-valued per creative** (FR-012a): every row of a creative shares the context sealed by the first of them to seal, so a creative can never hold two different sealed targets.
- **Contribution State** — a one-way state machine with exactly two states, PROVISIONAL and SEALED, carried on the contribution ledger entry, which is **per ad row** (FR-016). The **creative's** state is *derived* from its rows by FR-036c — SEALED if any row is SEALED, PROVISIONAL only while every row is — and the creative's sealed context is the one belonging to its first row to seal (FR-012a). The state is stored per row and read per creative; these are not the same thing and must not be conflated. PROVISIONAL means no target was resolvable yet; SEALED means the evaluation context is fixed. Only the PROVISIONAL → SEALED direction is reachable, and that constraint is enforced in the write path rather than assumed of callers.
- **Funnel Settings** — the existing source of the cost target and funnel type. Read-only to this feature.
- **Learning Lease** — one short-lived record per ad account, held only for the duration of that account's learning write. Carries a holder identity and an absolute expiry. Acquired and released atomically; expires on its own. It guards the ledger's check-then-act, and nothing else.

## Assumptions

- **No active users.** Existing aggregate and ad performance records may be retired without owner-visible loss, and no migration, backfill, or dual-read period is required.
- **Cost target resolution is unchanged.** The existing rule — paid funnels use the effective cost-per-acquisition target, free funnels the effective cost-per-lead target, and an unresolvable or unstamped economics payload yields no target — is consumed as-is, not modified.
- **The learning eligibility rules are unchanged.** Only ads with a confirmed creative link, available metadata, and a resolvable angle or pattern contribute. This feature changes how contributions are recorded and *counted*, not which ads qualify. **The eligibility CRITERIA are unchanged** — a resolvable generation, available metadata, a resolvable angle or pattern. **The unit they are evaluated over changes**: `isEligibleForLearning` (`functions/src/learningAggregates.ts:119-124`) is today a per-row predicate, and FR-074f requires it to be evaluated **per creative** instead, so that a creative whose link is propagated qualifies on the same terms as one whose link is direct. Nothing is relaxed; the predicate is applied at the unit Amendment 1 establishes.
  - **The effect on what data enters the aggregates is nonetheless wider, and planning MUST read it that way.** Under FR-074g, once a creative is eligible, the measured values of **rows that would individually fail the per-row predicate** — propagated-only rows, whose `matchType` is null — **do** enter learning, through their creative. This follows from FR-074's "the creative's evidence is the aggregate over all rows in the group" and so is not introduced by the eligibility change; but this is the sentence a planner checks when deciding what data reaches the aggregates, so it states the consequence rather than leaving the reading neutral.
- **The measurement window is unchanged.** The existing rolling window that feeds the verdict engine continues to define an ad's measured performance.
- **Funnel type comes from the account's funnel settings** at the moment of sealing. It is not inferred from the ad, the campaign, or the creative. When settings are absent or carry an unrecognised type, the funnel type is recorded as explicitly unknown.
- **The dashboard's tier icons continue to be derived from click-through against the account average.** The efficiency figure informs ordering and wording, not the icon tier, in this feature.
- **Concurrent and duplicate syncs are a live condition, not a hypothetical.** There is no per-account serialization today; a manual sync runs inline while scheduled syncs dispatch through a task queue, and that queue retries on failure, so an identical payload can be delivered more than once. The lease in section J exists for conditions the system already produces.
- **Both sync entry points are capped at 540 seconds by the platform.** The 15-minute lease time-to-live is derived from that ceiling rather than estimated from observed runtimes.
- **The existing task retry configuration is reused, not modified.** Three attempts with 30-to-600-second backoff already exists and is sufficient for lease contention.
- ~~**The manual sync's existing 1-hour cooldown remains in force** and independently makes manual-versus-manual contention rare.~~ **FALSE AS OF PHASE 970 — corrected.** Batch 4 of Phase 970 **removed** the 1-hour cooldown and replaced it with an in-flight guard (`functions/src/metaSync/trigger.ts:8`, `:54`; `functions/src/metaSync/orchestrator.ts:476`, `:651`). **Manual-versus-manual contention is therefore no longer rare** — nothing rate-limits a second manual press except the in-flight guard itself, and that guard is a lease, not a cooldown. The learning-write lease must be sized and justified without leaning on a cooldown that no longer exists.
  - *Flagged for Stage 1B*: FR-059's time-to-live justification still cites the cooldown as one of two self-clearing arguments (*"the manual path carries a 1-hour cooldown, so even a worst-case stranded lease self-clears"*). That half of the argument no longer holds. Section J is in scope in Stage 1B and FR-059 is corrected there; it is flagged here rather than left to stand.
- **Writes continue to use the sync's existing batched-commit path**, so the accumulation design must be expressible as per-record deltas applied within that path rather than as read-modify-write loops outside it.
- **The existing invariant that aggregates are not recomputed on generation delete is retained** and takes precedence over any general "withdraw on change" reading of the contribution rules.
- **Retrieval weighting strength is a tuning parameter**, not a behavioural contract. The contract is that same-funnel evidence ranks ahead of equivalent cross-funnel evidence and that cross-funnel evidence is never excluded; the exact weight is chosen during planning and may be adjusted without respecifying.
- **Bound and threshold values** (efficiency bound 3.0, minimum efficiency evidence 3, per-item top-performer floor 3, activation threshold 10) are stated as requirements here because they carry justification, but they are expected to be expressed as named constants so they can be revisited without a structural change. **Amendment 1 keeps all three counting thresholds at their existing numeric values (10 / 3 / 3) and changes their unit from ad rows to creatives (FR-073).** The numbers are unchanged; what they count is not, which at the observed 7.4:1 fan-out makes each gate roughly seven times harder to reach.
- **The activation threshold is provisional, not settled.** FR-034 retains the value 10 while recording that the evidence it represents has changed twice: first weakened (per-sync → all-time), then strengthened and re-based (ad rows → creatives, Amendment 1). It is carried forward because there is no data to calibrate a better value against, and it is expected to be revisited against real usage. Planning should not treat it as a fixed contract.
- **The `imageHash` grouping key is the only key currently exercised in production.** Account `act_995888422231015` has zero linked rows, so on that account the `generationId` branch of FR-074 is inert and every row resolves through the hash. Planning should not assume the linked path is well covered by real data; the fixtures must construct it.
