# Quickstart: Stripe Migration

**Branch**: `021-stripe-migration` | **Date**: 2026-05-05

This guide walks the merchant team and developer through the operational steps that must be completed in order for Phase 21 to ship. Code changes are tracked in `tasks.md` (generated by `/speckit.tasks`); this document covers the **non-code** dashboard setup and the smoke-test sequence.

## Prerequisites

- Stripe account, activated for live mode (Test mode for development).
- GHL account with admin access to Workflows and Funnels.
- Firebase Cloud Functions deployment access (`europe-west1` region).
- Domain `app.proadsai.com` configured for redirect URLs (success_url, return_url).
- Tax registration plan: confirm with the merchant team which jurisdictions require VAT/GST registration before launch.

---

## A. Stripe Dashboard Setup (Owner Steps — Not Code)

### A.1 — Account & API Version

1. Log in to [stripe.com](https://stripe.com). Activate the account (legal entity, bank account, identity verification).
2. Switch to **Test mode** for development.
3. Go to **Developers → API version**. Set **Default API version** to `2025-01-27.acacia` (or the current pinned version per `functions/src/stripe/stripeClient.ts`). This MUST match the SDK constructor's `apiVersion`.

**Acceptance**: Stripe account active. Test mode toggled. Default API version pinned to the same value as the SDK constructor.

### A.2 — Subscription Products

Create three subscription products with monthly and annual variants:

| Product | Monthly | Annual | Price ID (Monthly) | Price ID (Annual) |
|---|---|---|---|---|
| Starter | $29.00 USD | $290.00 USD (2 months free) | `price_starter_monthly` | `price_starter_annual` |
| Pro | $79.00 USD | $790.00 USD (2 months free) | `price_pro_monthly` | `price_pro_annual` |
| Scale | $197.00 USD | $1,970.00 USD (2 months free) | `price_scale_monthly` | `price_scale_annual` |

Set currency: **USD only** (R-016 — multi-currency is deferred).

Set billing cycle: monthly products use `interval: month`, annual use `interval: year`.

Set default trial period in `subscription_data` defaults: **7 days** (or override per Checkout Session — handled via callable).

**Acceptance**: 6 subscription price IDs recorded. All in USD. Annual variants priced at 10× monthly (i.e., 2 months free).

### A.3 — Top-Up Products

Create one one-time product **"Credit Top-Up"** with three prices:

| Pack | Price | Price ID |
|---|---|---|
| 100 credits | $9.00 USD | `price_topup_100` |
| 300 credits | $24.00 USD | `price_topup_300` |
| 800 credits | $59.00 USD | `price_topup_800` |

**Acceptance**: 3 top-up price IDs recorded. All in USD.

### A.4 — API Keys

1. Go to **Developers → API keys**.
2. Copy the **Secret key** (`sk_test_xxxxx` for test, `sk_live_xxxxx` for prod). This is `STRIPE_SECRET_KEY` in Cloud Functions secrets.
3. The **Publishable key** (`pk_test_xxxxx`) is NOT used by Phase 21 code (we redirect to hosted Checkout — no client-side Stripe.js needed). Optional: store it for future Payment Element use.

**Acceptance**: `STRIPE_SECRET_KEY` saved in Firebase Cloud Functions secrets manager.

### A.5 — Webhook Endpoint

1. Go to **Developers → Webhooks → Add endpoint**.
2. URL: `https://europe-west1-proadsai-saas.cloudfunctions.net/stripeWebhook`
3. **Events to subscribe to** (7 events):
   - `checkout.session.completed`
   - `customer.subscription.created`
   - `customer.subscription.updated`
   - `customer.subscription.deleted`
   - `invoice.payment_succeeded`
   - `invoice.payment_failed`
   - `charge.refunded`
4. Copy the **Signing secret** (`whsec_xxxxx`). This is `STRIPE_WEBHOOK_SECRET` in Cloud Functions secrets.
5. Set the API version on the webhook endpoint to match the pinned version (Stripe Dashboard → Webhooks → click endpoint → Settings → API version).

**Acceptance**: Webhook endpoint exists. All 7 events subscribed. Signing secret saved. API version matches pin.

### A.6 — Customer Portal Configuration

Go to **Settings → Billing → Customer portal**. Configure:

- **Subscription cancellation**: enabled. Cancellation policy: "At period end" (Stripe sets `cancel_at_period_end=true`).
- **Plan switching**: enabled. Allow customers to switch among the 6 subscription price IDs (Starter monthly/annual, Pro monthly/annual, Scale monthly/annual).
- **Payment method updates**: enabled.
- **Invoice history**: enabled.
- **Return URL**: `https://app.proadsai.com/billing`
- **Branding**: upload Pro Ads AI logo, primary color, favicon.
- **Localization**: enable English and Arabic.

**Acceptance**: Portal saves successfully. Test the portal manually with a sandbox customer to confirm cancellation, plan switch, and payment method update all work.

### A.7 — Stripe Tax

1. Go to **Settings → Tax → Tax settings**.
2. Enable **Stripe Tax** for automatic calculation.
3. Add tax registrations for jurisdictions where the merchant has nexus (consult merchant's accountant — for Arabic-market launch, likely **Saudi Arabia VAT** and **UAE VAT** at minimum, possibly **EU VAT MOSS** if EU customers are expected).
4. Confirm `automatic_tax: { enabled: true }` will be set in Checkout Session creation (handled in code per FR-027).

**Acceptance**: Stripe Tax enabled. Tax registrations recorded for at least the launch jurisdictions. Merchant team has acknowledged ownership of tax filing.

### A.8 — Smart Retries (Dunning)

1. Go to **Settings → Billing → Subscriptions and emails**.
2. Enable **Smart Retries**: 3 retries over 14 days (Stripe default).
3. Enable subscriber emails: "Card declined", "Payment retry succeeded", "Subscription canceled due to failed payments".

**Acceptance**: Smart Retries on. Email automations enabled.

## B. GHL Setup

### B.1 — Stripe Integration in GHL

1. In GHL, go to **Sub-account Settings → Integrations → Stripe**.
2. Connect the same Stripe account used in section A. (Use OAuth or API key per GHL's flow.)
3. Confirm GHL can create products and subscriptions in the connected Stripe account.

**Acceptance**: GHL is connected to the same Stripe account. Test by creating a $1 test product in GHL and confirming it appears in Stripe Dashboard.

### B.2 — Marketing Funnel Setup

1. Build the funnel pages in **GHL → Sites → Funnels** (already done in earlier phases — confirm pricing CTAs route to the GHL checkout form, not directly to Stripe Checkout URLs).
2. The GHL checkout form should be configured to charge the Stripe products from A.2 (Starter / Pro / Scale, monthly + annual).
3. Top-ups are **not** part of the GHL funnel — they are in-app only.

**Acceptance**: Funnel CTAs lead to GHL-hosted checkout form. Form is wired to the correct Stripe price IDs.

### B.3 — GHL Inbound Webhook Workflows (6 workflows, one per event type)

Per `contracts/ghl-inbound-payload.md`, Firebase POSTs to one of six dedicated GHL workflows depending on `event_type`. Each workflow uses the same payload schema (paste from §1 of the contract as the Mapping Reference). Create six "Inbound Webhook" workflows:

| GHL Workflow Name | Listens for `event_type` | Save URL as |
|---|---|---|
| Stripe — Trial Started | `trial.started` | `GHL_TRIAL_STARTED_URL` |
| Stripe — Payment Received | `subscription.created` | `GHL_PAYMENT_RECEIVED_URL` |
| Stripe — Payment Recovered | `payment.recovered` | `GHL_RECOVERED_URL` |
| Stripe — Payment Overdue / Failed | `payment.failed` | `GHL_OVERDUE_FAILED_URL` |
| Stripe — Subscription Cancelled | `subscription.cancelled` | `GHL_CANCELLED_URL` |
| Stripe — Top-Up Completed | `top_up.completed` | `GHL_TOPUP_URL` |

For each workflow:
1. Trigger: Inbound Webhook
2. Copy the GHL-generated URL (format: `https://services.leadconnectorhq.com/hooks/xxxxx`)
3. Paste the JSON schema from `contracts/ghl-inbound-payload.md` §1 into the Mapping Reference field so GHL knows the column shape
4. Add the per-event automations (welcome email, win-back, dunning, etc.) — no `event` field branching needed because each workflow only ever receives one event type
5. All 6 URLs are stored as Firebase Cloud Functions secrets — see section C

**Acceptance**: Six GHL workflows exist, each with an inbound webhook trigger and a unique URL. All 6 URLs saved. Test each by sending a manual POST with the contract's example payload (adjust `event_type` to match each workflow) and confirm the matching automation fires.

### B.4 — GHL Email Template Sanity

Email templates in any of the 6 workflows that reference `{{portal_url}}` should handle the case where `portal_url` is `null` (logged as `portal_session_generation_failed` inside the helper). Recommended fallback: render "Click here to manage your subscription" linking to `https://app.proadsai.com/billing` when `portal_url` is null/empty. The dunning email in **Stripe — Payment Overdue / Failed** is the most operationally important consumer of `portal_url`; the others may use it for convenience.

**Acceptance**: Email templates handle missing `portal_url` gracefully across all 6 workflows.

**Acceptance**: Stripe secrets set (2 Stripe + 6 GHL = 8 total). Paddle secrets destroyed. Verified via `firebase functions:secrets:list`.

## D. Code Migration Sequence

The migration PR follows this order to keep each commit reviewable:

1. **Add Stripe code** without removing Paddle (`functions/src/stripe/`, `functions/src/billing/stripeWebhook.ts`, new callables in `index.ts`)
2. **Update `billingState.ts`** to write Stripe fields; backfill compatibility with Paddle reads removed
3. **Update frontend** — pricing table, modal CTA, billing page, hooks
4. **Delete Paddle wholesale** — `functions/src/paddle/`, `paddleWebhook.ts`, 9 callables, Paddle.js loader, fixtures, tests
5. **Update `index.html`** to drop Paddle.js script tag
6. **Update i18n strings** (mostly UNCHANGED; remove any Paddle-specific copy)
7. **Run lint, build, and full test suite** — fix any compilation errors from the Paddle removal
8. **Smoke-test against Stripe test mode** (section E below)
9. **Open the PR** as a single atomic change; reviewers can browse the diff section by section

The PR may include intermediate commits but ships as a single PR per R-018.

## E. Smoke-Test Sequence (Stripe Test Mode)

Run before merging the migration PR. All tests use Stripe test cards (`4242 4242 4242 4242`).

### E.1 — In-App Subscription (Path B)

1. Create a fresh Firebase Auth account.
2. Verify email.
3. Land on the mandatory billing modal.
4. Click "Pro Monthly" → expect redirect to Stripe-hosted Checkout.
5. Pay with `4242 4242 4242 4242`.
6. Redirect back to `https://app.proadsai.com/billing?paid=1`.
7. **Expected**: success toast fires, modal auto-closes, `users/{uid}` has `plan: 'pro'`, `billingStatus: 'trialing'`, `stripeCustomerId`, `stripeSubscriptionId`. Welcome trial toast appears once.
8. Inspect Cloud Functions logs: confirm `checkout.session.completed` AND `customer.subscription.created` both received, second event recorded as `noop_dual_event`.

### E.2 — GHL Funnel Subscription (Path A)

1. Open the GHL funnel in incognito (no Firebase Auth account).
2. Pay via the GHL checkout form using a fresh email.
3. Inspect Stripe Dashboard: subscription created.
4. Inspect Cloud Functions logs: confirm webhook fired (either `checkout.session.completed` or `customer.subscription.created`). Confirm `pending_plans/{email.toLowerCase()}` document was written.
5. Visit `https://app.proadsai.com/login` and create a Firebase Auth account with the same email.
6. Verify email.
7. **Expected**: pending plan consumed into `users/{uid}`, pending document deleted, welcome toast fires, app loads without the mandatory modal.

### E.3 — Top-Up

1. As a paid user, go to Billing page.
2. Click 100-credit top-up.
3. Pay via Stripe Checkout (test card).
4. Redirect back to `https://app.proadsai.com/billing?topup=1`.
5. **Expected**: credit balance increases by 100 within 3 seconds. Success toast fires.

### E.4 — Cancel Subscription

1. As a paid user, click Cancel.
2. Submit reason in the in-app dialog.
3. Confirm `cancellation_logs/{uid}_{ts}` was written.
4. Redirect to Stripe Customer Portal `subscription_cancel` flow.
5. Confirm cancellation in the portal.
6. **Expected**: Billing page header shows "Cancelled — access until {date}". Webhook log shows `customer.subscription.updated` with `cancel_at_period_end=true`.
7. Wait for period end (or use Stripe Test Clock to simulate). On period end: `customer.subscription.deleted` fires, plan='none', credits=0.

### E.5 — Payment Failure & Recovery

1. Use Stripe test card `4000 0000 0000 0341` (charge succeeds, but next renewal will fail).
2. Use Stripe Test Clock to advance to next billing cycle.
3. **Expected**: `invoice.payment_failed` fires → Billing page shows "Payment failed" alert. GHL receives dunning sync with transient `portalUrl`.
4. Click "Update payment method" → opens Stripe Portal `payment_method_update` flow.
5. Update to `4242 4242 4242 4242`.
6. Stripe Smart Retries succeeds → `invoice.payment_succeeded` fires → alert disappears.

### E.6 — Refund (Subscription)

1. As a paid user, in Stripe Dashboard, issue a full refund for the latest subscription invoice.
2. **Expected**: `charge.refunded` fires → handler calls `stripe.subscriptions.cancel(stripeSubscriptionId)` → `customer.subscription.deleted` fires → plan='none', credits=0, billingStatus='cancelled'. GHL receives `refund_processed` event with amount + reason.

### E.7 — Refund (Top-Up)

1. As a paid user with credits from a top-up, in Stripe Dashboard, issue a full refund for the top-up payment.
2. **Expected**: `charge.refunded` fires → handler atomically deducts the top-up's `creditAmount` from `users/{uid}.credits` (clamped at zero). GHL receives `refund_processed`.

### E.8 — Refund (Partial)

1. Issue a partial refund (e.g., 50% of a subscription invoice).
2. **Expected**: handler logs `refund_processed` with source `partial`. No plan change. No credit change. `stripe_events/{eventId}.result = 'partial_refund_logged'`.

### E.9 — Webhook Replay

1. In Stripe Dashboard → Developers → Webhooks, click an already-delivered event and "Resend".
2. **Expected**: handler logs `stripe_event_duplicate` and returns 200. No state change.

### E.10 — Idempotency Under Load

1. Use the Stripe CLI: `stripe trigger checkout.session.completed --override mode=subscription`.
2. Trigger the same event 5x in rapid succession (simulate retry storm).
3. **Expected**: only the first arrival changes state. Subsequent 4 are deduped via `stripe_events/{eventId}` (atomic create).

## G. Rollback Plan

If a critical defect is discovered post-cutover:

1. Revert the migration PR (single revert click on GitHub).
2. Re-deploy Cloud Functions with the reverted code.
3. The reverted code restores Paddle. **However**: any users who paid via Stripe in the window between cutover and revert will have `stripeCustomerId` / `stripeSubscriptionId` on their `users/{uid}` document but no Paddle equivalent. These users will appear "unsubscribed" to the reverted code and may see the mandatory billing modal.
4. Manual remediation: refund those users in Stripe Dashboard, communicate the issue, ask them to resubscribe via Paddle once the system is restored.

Given this risk, the smoke tests in E.1–E.10 are non-negotiable. **Do not cutover** until all 10 pass.
